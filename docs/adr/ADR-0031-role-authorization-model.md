# ADR-0031: 역할·권한 모델 (통제별 역할 배정)

- 상태: 제안 (초안)
- 작성일: 2026-09-03
- 관련: ADR-0025(테넌트 자동 격리), ADR-0030(baseline 테넌트 소유권), ADR-0020(제로 추상화)
- 후속: ADR-0032(평가 회차·워크플로) — 본 ADR 확정 후 작성

---

## 1. 배경

증빙 관리·Test 모듈 설계 중 선행 결정이 필요함을 확인했다.

- 증빙 편집 권한이 "해당 통제의 평가자"에 달려 있는데 **통제별 담당자 배정 체계가 없다**
- 현재 권한은 admin / 일반 사용자 2단계뿐이다
- RCM 화면의 담당자 컬럼(`owner_name`)은 **문자열**이며 계정과 연결되어 있지 않다

역할이 정해지지 않으면 "누가 무엇을 할 수 있는가"를 쓸 수 없으므로 본 ADR을 선행한다.

### 1.1 조사 근거

국내 규정과 글로벌 실무를 조사한 결과(2026-09-03), 다음을 확인했다.

- 내부회계관리제도 평가 및 보고 기준(2023.12.29 제정)은 **평가자의 독립성**을
  감사위원회 검토 항목으로 명시한다
- 업무지침은 "내부회계전담부서(내부회계관리제도 평가자 포함)"로 기술하여
  **평가 주체가 전담부서 소속**임을 전제한다
- 글로벌 SOX 실무에서 통제 테스트는 전담 SOX 팀 또는 내부감사가 수행하며,
  경영진 자체평가만으로 끝나는 경우 독립성이 없다고 평가된다

### 1.2 용어 혼동 정리 — `reviewer`는 두 층에서 쓰인다

조사 중 발견한 혼동이다. **기록해 두지 않으면 반복된다.**

| 층 | 내용 | 용어 | 우리 시스템 |
|---|---|---|---|
| 통제 실행 | 통제 활동 그 자체 (예: 대사표 작성→팀장 검토) | preparer / reviewer / approver | **관리 대상 아님.** 통제 문서에 기술될 내용 |
| 통제 평가 | 통제가 잘 설계·운영됐는지 평가 | control owner / assessor / SOX PMO | **본 ADR의 대상** |

글로벌 문헌의 `creator/approver/reviewer` RBAC 논의는 대부분 **통제 실행 층**(ERP 등)을
말한다. 우리 시스템은 평가 층을 다루므로 그 용어를 그대로 가져오면 안 된다.

## 2. 결정

### 2.1 역할 정의

| 시스템 역할 | 글로벌 용어 | 국내 규정 용어 | 소속 |
|---|---|---|---|
| `control_owner` 통제책임자 | Control Owner | 통제책임자 | 실무부서 |
| `dept_approver` 부서승인자 | Control Owner의 상급자 | — | 실무부서 |
| `assessor` 평가자 | SOX PMO / Internal Controls Team | 평가자, 내부회계전담부서 | 전담부서 |
| `icfr_manager` 내부회계관리자 | Management | 내부회계관리자 | 경영진 |
| `ceo` 대표자 | CEO | 대표자 | 경영진 |
| `auditor` 감사 | Audit Committee | 감사, 감사위원회 | 감독기구 |
| `external_auditor` 외부감사인 | External Auditor | 외부감사인 | 외부 |
| `sys_admin` 시스템관리자 | — | — | — |

`external_auditor`는 **조회 전용**이다. 어떤 활동도 생성·수정하지 않는다.

`sys_admin`은 계정·설정 관리만 하며, **통제 관련 활동에 참여하지 않는다.**
시스템 관리 권한과 제도 운영 권한을 겸하면 그 자체가 감사 지적 대상이다.

### 2.1.1 'ITGC의 시스템'과 '본 시스템'은 다르다

내부회계관리제도의 통제활동에는 정보기술일반통제(ITGC)가 포함되며,
여기서 말하는 '시스템'은 회사가 실무에 사용하는 ERP·인사·자금 시스템 등을 가리킨다.
접근권한 관리, 변경관리, 운영관리, 백업·복구가 통제 대상이며 RCM에 담기는 통제활동이다.
통제책임자는 통상 IT부서 담당자다.

본 ICFR 시스템은 그 통제를 문서화하고 평가를 기록하는 도구이며,
통제 대상이 아니라 통제를 관리하는 도구다.
sys_admin은 본 시스템의 계정·설정만 관리하며 회사의 실무 시스템을 다루지 않는다.

혼동 시 발생하는 문제:
- sys_admin이 ITGC 통제책임자로 자동 배정되는 오류
- IT부서 담당자에게 sys_admin 권한을 부여해 제도 운영 데이터를
  직접 수정 가능하게 만드는 오류 (감사 지적 대상)

### 2.2 역할은 통제 단위로 배정한다

**사람에게 역할을 붙이지 않는다. 통제별로 붙인다.**

같은 사람이 통제 A에서는 통제책임자, 통제 B에서는 평가자가 될 수 있어야 한다.

**근거 — 중소기업 실무.** 관리부서가 4명(회계·인사·자금·총무)인 회사에서
회계 담당이 회계 통제의 통제책임자이면서 인사 통제의 평가자가 되는 상호 배정이
불가피하다. 제도 운영을 위해 인력을 별도 채용할 여건이 되지 않으며,
국내 실무에서 이러한 상호 배정이 허용되고 있다.

역할을 사람 속성으로 두면 이 구조를 표현할 수 없다.

### 2.3 배정 단위는 프로세스 기본값 + 통제별 예외

통제 93건 × 역할 4종을 개별 배정하면 372회 조작이 필요하다.

- 프로세스 단위로 기본 배정을 설정한다
- 통제별로 예외 지정이 가능하다
- 조회 시 통제별 지정이 있으면 그것이, 없으면 프로세스 기본값이 적용된다

이는 baseline/overlay와 같은 구조다. **저장은 차이만, 조회는 해석.**
ADR-0029 §2.1·§2.2의 원칙을 그대로 적용한다 — 프로세스 기본값이 바뀌면
개별 지정하지 않은 통제는 자동으로 따라간다.

### 2.4 이해상충 판정은 통제 단위로 한다

**판정 대상은 사람이 아니라 "이 통제에서의 조합"이다.**

| 조합 | 기본 | 사유 |
|---|---|---|
| 통제책임자 = 평가자 | ⚠ 경고 | 실무와 평가 주체가 같음. 규정상 평가자 독립성 저촉 소지 |
| 통제책임자 = 부서승인자 | ⚠ 경고 | 자기 작업을 자기가 승인 |
| 평가자 = 내부회계관리자 | ⚠ 경고 | 평가와 최종승인이 같음 |
| 그 외 겸직 | ✅ 허용 | 이해상충 없음 |

**막지 않는다. 경고하고 사유를 기록한다.**

막으면 중소기업이 시스템을 쓸 수 없고, 조용히 허용하면 감사에서 지적된다.
겸직 발생 시 사유를 남기게 하면 그 기록이 **보완통제 증적**이 된다.
글로벌 실무에서도 인원 규모상 완전 분리가 불가능한 경우
독립적 상급자 검토·이중 승인 등 보완통제를 문서화하도록 요구한다.

**관리자 토글로 허용 여부를 제어한다.** 기본은 허용(경고+사유 기록)이며,
`icfr_manager`가 특정 조합을 금지로 전환할 수 있다.

### 2.5 활동 3종과 역할의 매핑

| 활동 | 수행 | 승인 |
|---|---|---|
| 설계 / 설계변경 | 통제책임자 | 부서승인자(토글) → 평가자 |
| 설계평가 | 평가자 | 내부회계관리자 |
| 테스트(자체점검) | 통제책임자 | 부서승인자(토글) |
| 운영평가 | 평가자 | 내부회계관리자 |

**설계평가와 운영평가는 다른 활동이다.**
설계평가는 통제가 실무와 맞고 위험을 잡도록 설계됐는지를 본다
(예: 실무는 자동이체인데 통제 문서는 '인터넷뱅킹'으로 기술된 경우 → 설계 부적합).
운영평가는 설계대로 실제 운영됐는지를 본다.
글로벌 표준의 design effectiveness / operating effectiveness와 동일하다.

**테스트와 평가는 주체가 다르다.**
테스트(자체점검)는 실무부서가, 평가는 전담부서가 수행한다.
한국 실무에서 '자체점검'과 '통제항목 테스트'는 같은 의미로 통용된다.

### 2.6 부서승인 단계는 선택이다

실무부서 내부 승인(통제책임자 → 부서승인자)은 **관리자 토글로 켜고 끈다.**
인원이 적은 회사는 통제책임자와 부서승인자가 동일할 수 있다.

**단, 평가자는 통제책임자와 동일할 경우 §2.4의 경고 대상이다.**

### 2.7 최종 승인은 별도 단계다

평가 결과에 대해 `icfr_manager`가 최종 승인하면
대표자·이사회 보고 절차로 넘어간다. 이는 개별 통제 승인이 아니라
**평가 회차 전체에 대한 승인**이므로 ADR-0032에서 다룬다.

### 2.8 부서

부서는 팀장급이 책임지는 회사의 기능 조직 단위다.
예: 자금팀, 회계팀, 영업1팀, 개발1팀, 내부회계전담팀, 개발본부 직속부서.
dept_approver는 통제책임자가 속한 부서의 책임자다.

**본 시스템의 조직도는 회사 조직도의 스냅샷이며 원본이 아니다.**
인사시스템이 원본이고, 여기서는 전담부서 담당자가 현황을 옮겨 담는다.
발령·겸직·개편 같은 인사 로직은 구현하지 않는다.
관리 주체는 인사담당자가 아니라 내부회계전담부서 담당자다.

**계층 구조는 개념으로 보존하되 이번에는 평면으로 구현한다.**
- parent_id 컬럼을 두되 초기에는 전부 NULL로 운영한다
- 조회·배정 로직은 평면 목록 전제로 작성한다
- 본부·팀 계층이 필요해지면 값만 채우면 되도록 한다
근거: 스키마 변경은 횟수 자체가 위험이다(ADR-0030 경험).
나중에 컬럼을 추가하려면 마이그레이션이 또 필요하다.

**외부 연동 키를 둔다.** external_code 컬럼을 두어 향후 인사시스템 연동 시
매핑 키로 사용한다. 현재는 사용하지 않는다.

**스냅샷 시점 문제는 ADR-0032에서 다룬다.**
"당시 부서장이 누구였는가"는 감사 대응에서 실제로 묻는 질문이므로
역할 배정 이력과 함께 판단한다.

## 3. 영향 범위

| 대상 | 변경 |
|---|---|
| 신규 테이블 | 역할 배정(프로세스 기본값 / 통제별 예외) |
| 신규 테이블 | 이해상충 승인 이력(사유 기록) |
| 신규 테이블 | 테넌트별 정책 설정(토글) |
| 신규 테이블 | `departments` — 평면 구조. `parent_id`(초기 전부 NULL) + `external_code` 선반영 (§2.8) |
| `user_roles`(기존) | **테넌트 단위 역할 5종을 여기에 담는다** — 아래 정정 참조 |
| `users` | `users.role` 은 시스템 관리 권한으로 존치. 제도 운영 역할과 통합하지 않음 |
| `owner_name` | 문자열 컬럼. 계정 연결 여부는 별건 판단 |
| 권한 검사 | 기존 admin/일반 2단계 위에 통제별 역할 검사 추가 |

**모든 신규 테이블은 `AuditedBase`(테넌트 소유)로 둔다.** ADR-0030 §2.3의
복합 FK 격리를 동일하게 적용한다.

### 3.1 역할 저장소 결정 (2026-09-04 실측 반영)

초안 §3은 "`users` | 역할은 사용자 속성이 아님 — 변경 없음"이라고만 적었다.
**실측 결과 그 서술은 사실과 어긋났다 — 역할 저장소가 이미 3개 존재했고
이 ADR에 언급이 0건이었다.**

| 저장소 | 구조 | 실측 현황 |
|---|---|---|
| `users.role` | varchar(50), 전역 | `admin`/`reviewer`/`tester` 각 1. **`require_admin` 이 이 값을 본다** |
| `user_tenant_access.role` | varchar(50), 테넌트별 **단일값** | 3행. 판정에 쓰는 코드 0건 (§5 부채) |
| `user_roles` | `AuditedBase` + `user_id`·`role_name`·`scope` | 3행, `scope` 전부 NULL. CRUD·FE 배선 기존재 |

**결정**

- **테넌트 단위 역할 5종**(`icfr_manager`/`ceo`/`auditor`/`external_auditor`/`sys_admin`)은
  **기존 `user_roles` 를 재사용한다.** `AuditedBase` 라 테넌트 격리가 이미 걸려 있고,
  한 사람이 여러 역할을 가질 수 있으며, `/api/users/roles` CRUD와 FE 배선이 이미 있다.
  새 테이블을 만들면 저장소가 4개가 되어 무엇이 진실인지 판정할 수 없게 된다.
- **`users.role` 은 시스템 관리 권한으로 존치한다. 통합하지 않는다.**
- **통제 단위 역할 4종**(§2.3)은 신규 배정 테이블에 담는다.

### 3.2 `users.role` 과 `user_roles` 의 경계

**이 둘은 다른 것이며 서로 참조하지 않는다.**

| | `users.role` | `user_roles` |
|---|---|---|
| 의미 | **시스템 관리 권한** | **제도 운영 권한** |
| 범위 | 전역 계정 속성 | 테넌트 단위 |
| 값 | `admin` 등 | ADR-0031 역할 5종 |
| 판정 주체 | `require_admin` **전용** | 제도 운영 권한 검사 |
| 사용처 | 사용자 CRUD 4곳(생성·수정·삭제·비번리셋)뿐 | 회차·평가·증빙 권한 |

§2.1.1이 `sys_admin` 과 제도 운영 권한의 분리를 이미 적고 있다.
**그 구분이 저장소 수준에서도 유지된다는 뜻이다** — 시스템 계정을 관리하는 권한과
제도를 운영하는 권한은 같은 값을 공유하지 않는다.

한쪽을 보고 다른 쪽을 추론하지 않는다. `users.role == "admin"` 인 계정이
자동으로 `icfr_manager` 가 되지 않으며, 그 반대도 아니다.

## 4. 검증 조건

1. 같은 사용자가 통제 A에서 통제책임자, 통제 B에서 평가자로 배정 가능
2. 프로세스 기본값 변경 시 개별 지정 없는 통제에 자동 반영
3. 통제별 예외 지정이 프로세스 기본값보다 우선
4. 통제책임자 = 평가자 배정 시 경고 발생, 사유 없이는 저장 불가
5. 토글을 금지로 전환하면 해당 조합 배정이 거부됨
6. `external_auditor`는 어떤 생성·수정 API도 호출할 수 없음
7. 역할 배정이 다른 테넌트로 넘어가지 않음 (ADR-0030 격리)

**1번과 4번이 핵심이다.**
1번은 §2.2(통제 단위 배정)가, 4번은 §2.4(막지 않고 기록)가 구현됐는지 본다.

## 5. 미해결

- `owner_name` 문자열 컬럼과 `control_owner` 역할 배정의 관계.
  통합할지, 별개로 둘지 — 기존 데이터 93건에 이름이 들어있어 이관 판단 필요
- 역할 배정 변경 이력을 어느 수준까지 남길지 (ADR-0032 감사추적과 함께 판단)
- `user_tenant_access.role` 의 용도 — 세 번째 역할 저장소이나 판정에 쓰는 코드가 없다.
  단일값이라 겸직을 표현할 수 없어 §2.2와 충돌한다. 제거 또는 용도 확정 필요
  (`ClaudeICFR.md` 13.9-23)
- ~~조직도·부서 개념 도입 여부~~ ✅ **§2.8에서 해소** — 부서를 도입하되 회사 조직도의
  **스냅샷**으로 둔다(원본은 인사시스템). 계층은 `parent_id` 컬럼으로 개념만 보존하고
  평면으로 구현한다. 스냅샷 시점 문제는 ADR-0032
- 평가 회차별로 역할이 달라질 수 있는가 (예: 1분기 평가자와 2분기 평가자가 다름)
  → ADR-0032에서 다룬다
