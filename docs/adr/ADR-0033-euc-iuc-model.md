# ADR-0033: EUC·IUC 관리 모델

- 상태: 제안 (초안)
- 작성일: 2026-09-18
- 관련: ADR-0032(평가 회차·워크플로), ADR-0031(역할·권한), ADR-0030(테넌트 소유권), ADR-0020(제로 추상화)
- 근거 자료: `6__EUC_inventory.xlsx`, `7__IUC_inventory.xlsx` (실무 양식), 국내외 EUC 위험평가 표준

---

## 1. 배경

사이드바에 EUC·IUC 메뉴가 빈 화면으로 있다. 두 개념의 관계와 데이터 구조가
정의되지 않아 구현을 시작할 수 없다.

### 1.1 개념 정리

조사 과정에서 혼동이 있었으므로 기록해 둔다.

**EUC(End User Computing)는 ERP 안이 아니라 ERP 밖이다.**
실무 양식의 정의: "IT시스템 외부에서 데이터를 수정하기 위하여 사용되는 응용프로그램".

ERP 안에서 자동 계산되는 것은 시스템 통제이며 ITGC로 관리한다.
EUC는 **IT부서 통제를 받지 않는 도구** — 현업이 만든 엑셀·액세스·매크로 등이다.

| | ERP | EUC |
|---|---|---|
| 변경 절차 | IT부서 경유, 테스트·승인 | 담당자가 직접 수정 |
| 변경 흔적 | 남음 | 안 남음 |
| 검토 | 있음 | 없음 |
| 재무제표 영향 | 있음 | 있음 |

대손충당금·재고평가·감가상각 등을 엑셀로 계산하는 회사가 많다.
수식 하나가 틀려도 아무도 모른 채 재무제표로 들어간다.

### 1.2 EUC와 IUC의 관계

**IUC가 상위 개념이고 EUC는 그 한 종류다.**

- IUC — 통제에 쓰는 **정보**가 완전하고 정확한가
- EUC — 그 정보를 만드는 **파일** 자체를 어떻게 관리하는가

실무 양식이 이를 뒷받침한다. IUC 시트의 `정보 Type` 컬럼 값이
`EUC information` 이다. ERP 리포트라면 다른 값이 들어갈 자리다.

**둘은 같은 8건을 다룬다.** 유지보수매출·대손충당금·미수수익·금융상품평가·
미지급이자·연차충당부채·리스·이연법인세. 대시보드의 `ipe_relevant` 관련 8건과 일치한다.

별개 목록이 아니라 **통제의 두 측면**이다. 둘 다 통제활동번호로 묶인다.

## 2. 결정

### 2.1 데이터는 통제 중심 하나, 화면은 둘

**저장 구조를 EUC/IUC로 쪼개지 않는다.** 통제에 붙는 정보 항목 하나를 두고,
EUC 관점 필드와 IUC 관점 필드를 함께 갖는다.

화면은 사이드바 메뉴대로 둘을 유지한다.

| 화면 | 보여주는 것 |
|---|---|
| EUC | 파일명·설명·매크로 여부·위험평가·변경주기·저장소·관리부서·관리자 |
| IUC | 정보 Type·중요성·시스템/어플리케이션·기초정보·Report Logic·Input parameter·신뢰성 검토내역·설계평가 결과 |

**근거** — 두 테이블로 나누면 같은 8건이 두 곳에 생기고, 통제활동번호로
조인해야 한다. 오늘까지 저장소가 갈라져 생긴 문제를 여러 번 겪었다
(역할 3곳, risk-categories 읽기/쓰기 분리). 같은 대상을 둘로 나누지 않는다.

### 2.2 중요성 판단은 한 곳에서만 입력받는다

IUC의 `Information 중요성(H/M/L)`과 EUC 위험평가의 중요성 축은 같은 판단이다.

**한 곳을 주인으로 두고 다른 쪽은 참조한다.** 어느 쪽을 주인으로 할지는
구현 시 판단하되, **두 곳에서 각각 입력받지 않는다.** 값이 어긋날 수 있다.

### 2.3 EUC 위험평가는 복잡도 × 중요성 2축

국내외 표준이 일치한다 — 정량 평가가 복잡도를, 정성 평가가 중요성을 결정하며
이 둘이 위험의 두 주요 요인이다. Deloitte도 같은 기준을 쓴다.

| 축 | 판정 근거 |
|---|---|
| 복잡도 | 수식 구조 — 단순 기록 / 수식 기반 재가공 / 매크로·링크·모델 |
| 중요성 | 무엇으로 흘러가는가 — 규제·재무보고 / 경영보고 / 내부 운영 |

**이번에는 입력받는다. 자동 산출하지 않는다.**

복잡도는 파일 특성(매크로·외부링크·수식 수)이라 자동화 여지가 있으나,
현재 파일을 업로드하지 않고 목록만 관리하므로 판정할 대상이 없다.

**자동화는 후속 과제로 둔다.** 그때 자동 산출값을 입력값의 근거로 삼는다.
입력값을 덮어쓰지 않는다 — 판단은 사람이 하고 시스템은 근거를 제시한다.

### 2.4 위험 등급이 통제 식별 여부를 결정한다

실무 양식에 수식이 있다.

```
=IF(OR(위험평가="moderate", 위험평가="high"), "통제식별", "")
```

위험도가 moderate 이상이면 EUC 통제를 식별해야 한다.
이 판정을 코드로 옮긴다. **임계값을 하드코딩하지 않고 설정으로 둔다** —
회사마다 기준이 다를 수 있고, 감사인 협의로 조정된다.

### 2.5 EUC 통제 4종은 RCM 밖에서 관리한다

실무 양식의 EUC 관리 가이드라인이 정한 표준 통제다.

| 통제 | 내용 |
|---|---|
| 백업 관리 | 버전·백업 관리로 유효하지 않은 문서 사용을 방지 |
| 접근 관리 | 암호 보호 또는 접근 제한 디렉터리 저장 |
| 변경 관리 | 변경 전 백업, 변경 이력 관리 |
| 모니터링 관리 | 배포본과 통제 수행 시 사용본의 동일성 확인 |

**RCM 통제로 등록하지 않는다.** RCM은 재무보고 프로세스의 통제이고,
EUC 통제는 도구 관리 통제다. 성격이 다르고 실무에서도 분리해 관리한다.

EUC 파일마다 4종 통제가 붙고, 각각 담당자·검토자·증빙이 기록된다.

### 2.6 EUC 평가는 회차에 묶이되 RCM과 독립이다

ADR-0032 §2.2에서 설계평가 회차와 운영평가 회차를 독립으로 둔 것과 같다.
**회차 종류에 EUC 평가를 추가한다.** 새 개념을 만들지 않는다.

- EUC 평가 회차는 RCM 회차와 별도로 열고 닫는다
- 마감·최종승인 등 회차 워크플로는 ADR-0032를 그대로 따른다
- 권한도 ADR-0031을 그대로 따른다

**근거** — 실무에서 EUC 평가를 RCM 평가와 별도 일정으로 진행한다.
같은 회차에 묶으면 한쪽이 안 끝나 다른 쪽을 마감하지 못한다.

### 2.7 정보 Type은 확장 가능하게 둔다

현재 실무 양식에는 `EUC information` 하나만 나타난다.

**지금은 그 값만 지원하되 값 목록을 확장 가능한 형태로 둔다.**
ERP 리포트(`System generated`) 등이 나중에 추가된다.

값 목록은 한 곳에 정의한다. 대시보드 0건 미표시 사건(ClaudeICFR.md 13.9-40)의
교훈이다 — 값 집합이 상수로 없으면 데이터에 있는 값만 나열하게 된다.

## 3. 영향 범위

| 대상 | 변경 |
|---|---|
| 신규 | 정보 항목 (통제×정보, EUC·IUC 필드 통합) |
| 신규 | EUC 통제 (파일별 4종, 담당자·검토자) |
| 신규 | EUC 통제 평가 기록 |
| 평가 회차 | `kind` 에 EUC 평가 추가 |
| 테넌트 정책 | 위험 등급 임계값 |
| 대시보드 | EUC·IUC 카드 — 현재 "준비중" |

**모든 신규 테이블은 `AuditedBase`로 둔다.** ADR-0030 §2.3의 복합 FK 격리를 적용한다.

RCM의 `euc_description`·`related_systems`·`ipe_relevant` 필드와의 관계를
구현 시 확인할 것. 중복이면 정리하고, 다른 용도면 그 사실을 기록한다.

## 4. 검증 조건

1. 통제에 정보 항목을 등록하면 EUC·IUC 양쪽 화면에서 보임
2. 중요성을 한 곳에서 수정하면 다른 화면에도 반영됨 (두 곳 입력 아님)
3. 복잡도·중요성 입력 → 위험 등급 자동 산출
4. 위험 등급이 임계값 이상이면 통제 식별 대상으로 표시
5. 임계값을 설정에서 바꾸면 판정이 바뀜 (하드코딩 아님)
6. EUC 파일에 4종 통제가 붙고 담당자·검토자 지정 가능
7. **EUC 평가 회차를 RCM 회차와 동시에 열 수 있고 서로 영향 없음**
8. EUC 통제가 RCM 통제 목록에 나타나지 않음
9. 정보 Type 값 목록이 상수에서 오고, 미사용 값도 선택지에 나타남
10. 다른 테넌트의 EUC·IUC에 접근 불가

**2번과 7번이 핵심이다.**
2번은 §2.2(중요성 단일 입력), 7번은 §2.6(회차 독립)이 구현됐는지 본다.

## 5. 미해결

- 위험평가 자동 산출 — 파일 업로드 후 매크로·외부링크·수식 수를 분석해
  복잡도를 제시하는 것. 파일 업로드 기능이 선행되어야 한다
- EUC 파일 실물 보관 여부 — 현재 양식은 저장소 경로만 기록한다.
  파일 자체를 시스템에 올릴지는 별도 판단
- IUC의 `설계평가 결과` 컬럼과 ADR-0032 설계평가 회차의 관계.
  같은 것인지 별개인지 구현 시 확인
- RCM `ipe_relevant` 필드와 IUC 목록의 정합성 —
  현재 관련 8건이 일치하나 양쪽에서 각각 관리되면 어긋난다
