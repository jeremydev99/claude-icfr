# ADR-0038: 검토·승인 거버넌스 — 관리자 4단계·자기 승인 금지·재오픈 승인·변경 이력

- 상태: **채택** (2026-10-03 마스터 결정, 1단계 구현 — 마이그레이션 `9b2c4d6e8f10`)
- 관련: ADR-0031(역할·권한), ADR-0034(스코핑 상태·확정 스냅샷), ADR-0036(감사 컬럼 행위자)

## 1. 배경

내부회계 감사는 **검토·승인 통제가 실제로 작동했는지**를 증거로 본다 — 누가·언제 검토했고, 승인자는 작성자와 다른
사람이며, 승인 뒤 변경이 통제되고 기록되는가. 2026-10-03 점검 결과 현재 구조는 그 증거가 지워지거나 성립하지 않는다.

| 항목 | 현재 | 문제 |
|---|---|---|
| 항목별 "확인"(스코핑 템플릿 값 배지) | 확인자·시각 저장 | 확인 취소·수정 시 **덮어써 사라짐** |
| 스코핑 상태 작성 중→검토 중→확정 | 상태 이력(행위자·사유·스냅샷) 있음 | **같은 사람이 검토 요청과 확정**을 모두 할 수 있음 |
| 확정 후 재오픈 | 사유만 쓰면 즉시 작성 중 | **승인 없음** — 확정자가 혼자 풀고 고침 |
| 값 수정 | 마지막 수정자(updated_by)만 | **수정 전·후 값**이 남지 않음 |
| 관리자 단계 | 내부회계 관리자 단계가 `icfr_manager` 하나뿐 | 담당 직원·조직장·관리자(CFO)를 구분할 수 없어 작성·검토·승인 분리가 불가 |

## 2. 결정

### 2.1 관리자 4단계 (테넌트 역할, `user_roles`)

| 단계 | 역할 코드 | 누구 | 할 수 있는 것 |
|---|---|---|---|
| 1 일반관리자 | `icfr_staff` (신규) | 내부회계 담당부서 직원 전체 | 작성·수정, 항목 확인, 검토 요청, 재오픈 요청 |
| 2 책임관리자 | `icfr_lead` (신규) | 담당부서 조직장 | 1 + **검토 완료**(작성자가 아닐 때) |
| 3 마스터관리자 | `icfr_manager` (기존 이름 유지) | 내부회계관리자(통상 CFO) | 2 + **최종 승인(확정)**·**재오픈 승인**·역할 배정 |
| 4 시스템관리자 | `sys_admin` (기존) + `users.role=admin` | 시스템 운영자 | 계정·설정만. **검토·승인 등 제도 업무 불가** |

- **1~3단계는 한 사람에 하나만**(중복 배정 불가 — 서버가 409). 단계를 바꾸려면 기존 단계를 해제하고 새로 배정한다
  (해제·배정 모두 이력). 한 사람이 둘을 가지면 "작성자 ≠ 승인자"가 형식만 남는다.
- **4단계(시스템관리자)는 1~3단계 중 하나와 중복 가능**(2026-10-03 마스터). 
- 상위 단계는 하위 단계의 권한을 포함한다(판정은 `core/permissions` 한 곳).
- `icfr_manager` 코드는 바꾸지 않는다 — 이미 쓰는 가드·데이터를 깨지 않기 위함. 화면 이름만 "마스터관리자(내부회계관리자)".
- 기존 ADR-0031 역할(`ceo`·`auditor`·`external_auditor`·통제 단위 역할)은 그대로 둔다.

### 2.2 자기 승인 금지 (예외 없음)

한 문서(스코핑 회계연도 등)에서 **작성(검토 요청)한 사람, 검토한 사람, 승인한 사람은 서로 달라야 한다.**

- 검토자 ≠ 검토 요청자, 승인자 ≠ 검토 요청자, 승인자 ≠ 검토자.
- **작성자 단계에 따라 승인 경로가 정해진다**(2026-10-03 마스터):

  | 작성(검토 요청)자 | 경로 |
  |---|---|
  | 일반관리자 | 작성 → **책임관리자 검토**(작성자 아님) → **마스터 승인** |
  | 책임관리자 | 작성 → **마스터 승인** (조직장 작성분은 검토 단계를 두지 않는다 — 검토할 상위 조직장이 없고, 마스터 승인이 독립 확인이다) |
  | 마스터관리자 | 작성 → **외부 승인**: 대표이사 또는 이사회. 보고서를 출력해 대표이사 보고·이사회 보고(의사록)로 마무리하고, **외부 절차 증빙(의사록·결재 문서 스캔)을 시스템에 첨부해 확정**한다(§2.2.1) |

  일반관리자 작성인데 책임관리자가 0명이면 검토 단계 없이 마스터 승인으로 간다.
  현재 운영(노정희 = 책임관리자, 마스터 1명)은 **노정희 작성 → 마스터 승인**이다.
- 위반은 서버가 409 로 거부한다(화면 숨김만으로 막지 않는다).

#### 2.2.1 외부 승인 기록 (대표이사·이사회)

마스터 작성 문서는 시스템 안에 승인자가 없다 — 승인은 회사의 외부 절차(대표이사 결재, 이사회 보고·결의)에서 일어난다.
시스템은 그 결과를 **증빙과 함께 기록**한다:
- 상태: 검토 요청 → **외부 승인 대기** → (증빙 등록) → 확정.
- 등록 항목: 승인 기관(`ceo` 대표이사 / `board` 이사회), 승인일, 회의·결재 식별(예: "제5차 이사회"), **증빙 파일 1개 이상(필수)**.
- 등록은 일반관리자 이상 누구나(문서 작성자 포함) 할 수 있다 — 승인 행위가 아니라 **이미 일어난 외부 승인의 기록**이기 때문.
  대신 증빙 파일 없이는 확정되지 않고, 등록자·시각·파일이 이력에 남는다.
- 출력 양식(대표이사 보고서·이사회 보고서)은 Report 화면 양식을 쓴다(13.9-78). 의사록 양식 생성은 범위 밖 — 스캔 첨부만.

### 2.3 확정 후 잠금과 재오픈 승인

- 확정되면 해당 문서의 모든 쓰기는 409(기존과 같음).
- 재오픈은 2단계: **재오픈 요청**(일반 이상, 사유 필수) → **재오픈 승인**(마스터관리자, 요청자 ≠ 승인자) → 작성 중.
  거절도 사유와 함께 기록한다. **마스터 본인이 요청한 재오픈은 §2.2.1 과 같이 대표이사·이사회 외부 승인 증빙으로 승인한다.**
- 재오픈 시 **버전(`version`)을 올리고** 이전 확정 스냅샷은 이력에 그대로 남긴다(현재처럼 비우되 사라지지 않게).

### 2.4 변경 이력 — 지울 수 없는 기록

신규 테이블 `governance_events` (테넌트 소속, append-only):
`entity_type`·`entity_id`·`action`·`actor_id`·`at`·`reason`·`before`(JSON)·`after`(JSON)·`version`.

- action: `item_confirm`·`item_unconfirm`·`value_change`·`submit_review`·`review_done`·`review_return`·`approve`·
  `reopen_request`·`reopen_approve`·`reopen_reject`.
- **수정·삭제 API 없음.** PostgreSQL 트리거로 UPDATE·DELETE 를 거부한다(앱 버그로도 못 지움).
- 항목 확인 취소·값 수정 시 **이전 확인자·값을 이 테이블에 남긴 뒤** 현재 행을 바꾼다 — 현재 행은 "지금 상태", 이력은 이 테이블.
- 화면: 문서마다 "이력" 탭(누가·언제·무엇을·전→후·사유).

### 2.5 시스템관리자 — 1~3단계와 겸직 허용, 권한은 섞지 않음

- **겸직 허용**(마스터 결정 2026-10-03): `sys_admin` 은 1~3단계 중 하나와 함께 가질 수 있다. 경고·사유 요구 없음.
  ADR-0031 §2.1 의 "겸직은 지적 대상" 서술은 이 결정으로 대체한다(인원이 적은 조직의 현실).
- 대신 **권한은 섞지 않는다**: 검토·승인·확정·재오픈 승인 권한은 오직 1~3단계 역할에서 나온다.
  `sys_admin` 만 가진 계정은 제도 업무를 할 수 없고, `sys_admin` 이 있다고 승인 단계가 올라가지 않는다.
- 현재 운영(마스터 계정 = `sys_admin` + `icfr_manager`)은 이 규칙에 맞는다 — 변경 없음.
- 사용자 계정 관리(생성·비밀번호 재설정)는 `users.role=admin` 이 계속 한다(ADR-0031 §3.2 경계 유지).

## 3. 적용 순서

1. **1단계 — 공통 틀 + 스코핑**: 역할 2종 추가, `governance_events`(+트리거), 권한 판정 함수, 자기 승인 금지,
   재오픈 요청/승인(`reopen_requests` 테이블), 스코핑 항목 확인 이력·값 변경 이력, 화면(승인 패널·이력 탭·
   대시보드 "내 결재 대기"). 마이그레이션은 **추가만**(기존 데이터 변경 없음).
2. **2단계 — 같은 틀 확장**: RCM 확정, 평가(테스트) 결론, 미비점 평가, 재무제표 확정.

## 4. 검증 조건

1. 검토 요청자가 검토·승인하면 409, 검토자가 승인하면 409.
2. 책임관리자 0명이면 검토 단계 없이 작성자 ≠ 승인자로 확정된다.
3. 확정 후 재오픈 요청만으로는 상태가 바뀌지 않고, 요청자 본인 승인은 409, 다른 마스터 승인 시 작성 중 + 버전 +1.
4. 항목 확인 → 취소 → 재확인 이력 3건이 남고 각 행위자가 보존된다.
5. `governance_events` UPDATE·DELETE 는 DB 에서 거부된다.
6. `sys_admin` 만 가진 계정은 검토·승인 API 가 403. `sys_admin`+1~3단계 겸직은 배정 허용.
7-1. 1~3단계 중 하나를 가진 사람에게 다른 1~3단계를 배정하면 409.
7. 기존 스코핑(2026 작성 중) 데이터는 마이그레이션 전후 동일.

8. 마스터가 검토 요청한 문서는 내부 승인 API 가 409, 증빙 없는 외부 승인 등록은 422, 증빙과 함께 등록하면 확정.

## 5. 결정 기록

- 2026-10-03 마스터: 1~3단계 중복 불가·4단계 중복 가능, 자기 승인 금지, 재오픈 승인 필요, 마스터 작성분은 대표이사·이사회
  외부 승인 + 증빙 스캔 관리, 노정희 = 책임관리자.
