# 2-A-4-4: 어서션 junction CRUD overlay 전환

작성일: 2026-08-24
근거 ADR: ADR-0029(cascade 시맨틱) §2.3·§2.4, ADR-0020(제로 추상화)
관련: ClaudeICFR.md 13.3(2-A-4-3 범위), 잔여 xfail `test_search_response_includes_assertions`

---

## 0. 배경

2-A-4-3에서 상위 3계층 조회·CRUD가 overlay로 전환됐으나, **어서션 junction CRUD만 남았다.**

- 조회는 `_resolve_assertions`로 resolver 경유 (전환 완료)
- 쓰기는 `POST /control-assertions`가 여전히 legacy `control_assertions` 테이블에 씀
- 즉 **읽는 곳과 쓰는 곳이 다른 상태**가 어서션에만 남아 있다

이는 2026-08-24 오전에 상위 3계층에서 발견·수정한 것과 **동일한 구조적 결함**이다.
운영 서버에서 어서션 연결을 수정하면 화면에 반영되지 않는다.

13.3의 2-A-4-3 범위에 포함돼 있었으나 2026-08-24 프롬프트 §1에서 누락되어 미완으로 남았다.

## 1. 범위

**포함**
- 어서션 junction CRUD를 `control_assertion_instances` 기반으로 전환

- ADR-0029 §2.4(통제 제외 시 연결도 함께 제외) 쓰기 경로 정합성 확보

**제외**

## 2. 사전 실측 (STEP 0 — 추정 금지)

**아래를 확인하기 전에 코드를 쓰지 않는다.** 스키마는 확인했으나 처리 방식은 코드에 있다.

### 2.1 소프트 삭제 처리 방식 — 판단이 갈리는 지점

`control_assertion_instances`에 `is_deleted` 컬럼이 존재한다.
동시에 아래 유니크 제약이 걸려 있다.

```
uq_control_assertion_instances_tenant_baseline_rc
  (tenant_id, control_baseline_id, baseline_risk_category_id)
uq_control_assertion_instances_tenant_instance_rc
  (tenant_id, control_instance_id, baseline_risk_category_id)
```

**문제** — `is_deleted=true`로 소프트 삭제하면 그 행이 유니크 제약을 계속 점유한다.
같은 통제-어서션 쌍을 다시 조작할 때 제약 위반이 발생한다.

확인할 것:
- 다른 instance 테이블(`control_instances`, `process_instances` 등)의 삭제 처리가
  물리 삭제인지 `is_deleted` 소프트 삭제인지. **기존 선례를 따를 것**
- 소프트 삭제라면 유니크 제약 충돌을 어떻게 회피하고 있는지 (부분 인덱스? 재활성화?)
- 선례가 없거나 어서션 junction에 적용 불가하면 **중단하고 보고**

```bash
grep -rn "is_deleted" backend/app/api/rcm.py | head -30
grep -rn "is_deleted" backend/app/services/control_resolver.py | head -20
```

### 2.2 이중 nullable FK 분기 방식

`control_baseline_id` / `control_instance_id` 중 하나만 채워야 한다
(`ck_control_assertion_instances_single_parent`).

- 통제가 baseline 유래(`action` in adopt/exclude/override) → `control_baseline_id`
- 통제가 tenant 신규(`action='add'`) → `control_instance_id`

기존 `_resolve_assertions`가 이 분기를 어떻게 읽는지 확인하고, **쓰기도 동일 규약을 따를 것.**
읽기와 쓰기가 다른 규약을 쓰면 이 작업의 목적 자체가 무너진다.

```bash
sed -n '/_resolve_assertions/,/^def /p' backend/app/services/control_resolver.py
```

### 2.3 현재 쓰기 경로

```bash
grep -n "control-assertions\|control_assertions" backend/app/api/rcm.py
```

legacy 테이블에 쓰는 핸들러의 위치와 시그니처를 보고할 것.

**보고할 것 3건**
1. 소프트 삭제 선례와 유니크 제약 충돌 회피 방식
2. `_resolve_assertions`의 이중 FK 분기 규약
3. 현재 legacy 쓰기 핸들러 위치

**실측이 ADR-0029 §2.3·§2.4 전제와 어긋나면 코드를 맞추지 말고 보고할 것.**

## 3. 결정 사항

### 3.1 떼었다 다시 붙이면 `remove` 레코드를 삭제한다

유니크 제약이 한 쌍당 레코드 하나를 강제하므로, `remove`와 `add`가 공존할 수 없다.
따라서 선택지는 "remove 레코드 삭제" 또는 "add로 전환" 둘뿐이다.

**삭제를 택한다.** baseline이 진실이고 overlay는 차이만 담는다.
차이가 없어지면 레코드도 없어야 한다. `add`로 전환하면 baseline에 이미 있는 연결이
overlay에도 중복 표현되어, 같은 상태가 두 가지로 표현 가능해진다.

단, 물리 삭제인지 소프트 삭제인지는 **STEP 0 §2.1 실측 결과를 따른다.**

### 3.2 baseline에 없는 연결을 붙이면 `add`

`ASSERTION_ACTION_ADD`. baseline junction에 없는 통제-어서션 쌍을 새로 만드는 경우다.

### 3.3 baseline에 있는 연결을 떼면 `remove`

`ASSERTION_ACTION_REMOVE`. baseline junction 레코드는 건드리지 않는다.

### 3.4 action 상수만 사용

6ba94a4에서 정의한 `ASSERTION_ACTION_ADD` / `ASSERTION_ACTION_REMOVE`만 참조한다.
문자열 리터럴 금지. 계층 overlay 상수(`ACTION_ADD` 등)와 혼용 금지 —
값이 `"add"`로 겹치므로 상수명으로만 구분된다.

### 3.5 통제 제외 시 연결 처리 (ADR-0029 §2.4)

통제가 제외되면 그 연결도 effective 제외다. 이는 **조회 시점 계산**이며,
쓰기 시점에 junction 레코드를 물리적으로 건드리지 않는다(ADR-0029 §2.1·§2.2 동일 원칙).

즉 통제 제외는 junction CRUD의 관심사가 아니다. 다만 **제외된 통제에 대해
연결 추가/삭제 요청이 오면 어떻게 할지**는 정해야 한다.

**결정: 거부하지 않고 허용한다.** 제외는 되돌릴 수 있는 상태이고,
제외 중에 편집한 내용은 복원 시 살아나야 한다(ADR-0029 §2.2의 복원 원칙과 동일).
조회에서 안 보이는 것과 편집 불가는 다른 문제다.

## 4. 구현 원칙

- ADR-0020 준수. 서비스 클래스·패턴 금지, 직접 함수와 명시적 분기만
- 기존 `_apply_control_update` / `create_control` 의 구현 방식을 따를 것
- 읽기(`_resolve_assertions`)와 쓰기가 **동일한 FK 분기 규약**을 쓸 것

## 6. 검증 조건

테스트로 구현할 것.

1. baseline에 없는 연결 추가 → `action='add'` 레코드 생성, 조회에 반영
2. baseline에 있는 연결 제거 → `action='remove'` 레코드 생성,
   **baseline junction 레코드는 변경되지 않음**
3. 제거한 연결을 다시 추가 → `remove` 레코드가 사라지고 baseline 상태로 복귀.
   `add` 레코드가 새로 생기지 않을 것
4. `action='add'` 통제(tenant 신규)의 연결이 `control_instance_id`에 매달림
5. baseline 통제의 연결이 `control_baseline_id`에 매달림
6. 제외된 통제에 대한 연결 편집이 허용되고, 통제 복원 시 그 편집이 반영됨
7. 잔여 xfail `test_search_response_includes_assertions` 해소 (XPASS strict로 확인)

**2번과 3번이 핵심이다.** 2번은 baseline 불변을 지키는지, 3번은 §3.1 결정이
실제로 구현됐는지 본다. 3번이 없으면 `add`로 전환하는 잘못된 구현도 통과한다.
