# 3-1: 부서 + 역할 배정 구현 (ADR-0031 1단계)

작성일: 2026-09-03
근거 ADR: ADR-0031(역할·권한 모델), ADR-0030(테넌트 소유권), ADR-0025(테넌트 자동 격리), ADR-0020(제로 추상화)
후속: 3-2 평가 회차·워크플로(ADR-0032 §2.1~2.6), 3-3 증빙(§2.7)

---

## 0. 이 단계의 위치

ADR-0031·0032가 담은 범위를 세 단계로 나눈 첫 번째다.

| 단계 | 범위 | 근거 |
|---|---|---|
| **3-1 (본 작업)** | 부서 + 역할 배정 | ADR-0031 |
| 3-2 | 평가 회차 + 워크플로 | ADR-0032 §2.1~2.6 |
| 3-3 | 증빙 | ADR-0032 §2.7 |

**1단계가 선행인 이유** — 회차 워크플로가 역할을 참조하고(누가 승인하는가),
증빙 권한이 역할과 회차 상태 양쪽에 달려 있다. 순서를 바꾸면 참조 대상이 없다.

## 1. 범위

**포함**
- `departments` 테이블 (평면 구조, `parent_id`·`external_code` 선반영)
- `user_departments` 매핑 (다중 소속, 주 소속 플래그)
- 역할 배정 (프로세스 기본값 + 통제별 예외)
- 이해상충 경고 + 사유 기록
- 테넌트 정책 설정 (토글)
- 위 전부의 CRUD API

**제외**
- 평가 회차·워크플로 → 3-2
- 증빙 → 3-3
- `owner_name` 이관 → **하지 않기로 결정** (§2.4)
- 계층 조직도 로직 → `parent_id` 컬럼만 두고 평면으로 구현 (ADR-0031 §2.8)

## 2. 설계 확정 사항

### 2.1 부서

```
departments
  name            부서명 (예: 자금팀, 회계팀, 내부회계전담팀)
  manager_id      부서 책임자 (users FK)
  parent_id       상위 부서 (NULL로 시작, 계층 확장 대비)
  external_code   인사시스템 연동 키 (현재 미사용)
```

- **한 사람이 여러 부서의 책임자가 될 수 있다.** `manager_id` 중복 허용.
  근거: 본부장이 팀장 퇴사 시 팀장을 겸임하는 경우가 실재한다
- `parent_id`는 초기 전부 NULL. 조회·배정 로직은 평면 전제로 작성한다
- 조직도는 회사 조직도의 **스냅샷**이다. 발령·개편 같은 인사 로직을 구현하지 않는다

### 2.2 사용자–부서 매핑

```
user_departments
  user_id
  department_id
  is_primary      주 소속 여부
```

- **한 사람이 여러 부서에 소속될 수 있다.** 근거: 회계팀 직원이 내부회계전담팀을
  겸하는 등 중소기업에서 실재한다
- **주 소속은 정확히 하나다.** 사용자당 `is_primary=true`가 1건임을 보장할 것

### 2.3 역할 배정

ADR-0031 §2.1의 역할 8종 중 **통제별로 배정되는 것은 4종**이다.

| 배정 대상 | 비고 |
|---|---|
| `control_owner` | 통제별 배정 |
| `dept_approver` | 통제책임자의 주 소속 부서 책임자에서 **유도**. 통제별 개별 지정 가능 |
| `assessor` | 통제별 배정 |
| `icfr_manager` | 테넌트 단위 (통제별 아님) |

`ceo` / `auditor` / `external_auditor` / `sys_admin`은 테넌트 단위 역할이며
통제에 배정되지 않는다.

**배정 구조는 프로세스 기본값 + 통제별 예외다.**

- 프로세스 단위로 기본 배정을 설정한다
- 통제별로 예외 지정이 가능하다
- 조회 시 통제별 지정이 있으면 그것이, 없으면 프로세스 기본값이 적용된다
- **저장은 차이만, 조회는 해석** — ADR-0029 §2.1·§2.2와 같은 원칙

응답에 **출처를 표시할 것.** 프로세스 기본값에서 온 값인지 통제별 지정인지를
FE가 구분할 수 있어야 한다(RCM의 `source` envelope과 같은 개념).

### 2.4 `owner_name`은 이관하지 않는다

`baseline_controls.owner_name`은 문자열이며 **통제 문서에 기재된 수행자 서술**이다.
역할 배정과는 다른 개념이므로 이관하지 않고 그대로 둔다.

근거:
- 실제 데이터에 "솔루션사업팀" 같은 **팀 이름**이 들어 있어 계정 매핑이 불가능하다
- "노정희, 유헌종"처럼 **복수 인물**이 한 칸에 들어간 경우가 있다
- 이관하면 RCM 문서 서술이 계정 존재 여부에 종속된다. 퇴사자 발생 시 문서가 깨진다

**대신 배정 화면에서 참고 정보로 제공한다.** API 응답에 `owner_name`을 함께 실어
FE가 "문서상 수행자: 김세영"을 표시할 수 있게 한다. 초기 배정 힌트가 되고,
배정과 어긋나면 그 자체가 검토 대상이 된다.

### 2.5 이해상충

**막지 않는다. 경고하고 사유를 기록한다.**

| 조합 | 기본 동작 |
|---|---|
| `control_owner` = `assessor` | 경고 + 사유 필수 |
| `control_owner` = `dept_approver` | 경고 + 사유 필수 |
| `assessor` = `icfr_manager` | 경고 + 사유 필수 |
| 그 외 | 통과 |

- **판정은 통제 단위다.** 사람 단위가 아니다. "이 통제에서 이 조합인가"만 본다
- 사유 없이는 저장 불가
- 사유는 이력으로 보존한다 (보완통제 증적)
- 테넌트 정책 토글이 금지로 켜져 있으면 저장 자체를 거부한다 (409)

### 2.6 테넌트 정책 설정

```
tenant_policies
  dept_approval_enabled        부서승인 단계 사용 여부 (기본 true)
  conflict_* (조합별)          이해상충 조합별 허용 여부 (기본 허용)
```

`icfr_manager`만 변경할 수 있다.

3-2·3-3에서 항목이 추가되므로(증빙 편집 토글, 보존기간) **확장 가능한 형태**로 둘 것.
다만 지금 필요 없는 컬럼을 미리 만들지는 않는다.

## 3. 사전 실측 (STEP 0)

**스키마와 기존 구조를 추정하지 않는다.**

```bash
# 3-1. users 테이블 실제 구조
docker compose exec postgres psql -U icfr -d icfr_db -c "\d users"

# 3-2. 기존 권한 체계 — admin/일반 구분이 어디서 이뤄지는지
grep -rn "is_admin\|role\|CurrentUser" backend/app/core/ backend/app/api/deps*.py | head -20

# 3-3. owner_name 실제 값 분포 (이관 안 하지만 참고 제공 대상)
docker compose exec postgres psql -U icfr -d icfr_db -c \
  "SELECT owner_name, count(*) FROM baseline_controls GROUP BY owner_name ORDER BY 2 DESC;"

# 3-4. AuditedBase / TenantMixin 정의 재확인
grep -n -A15 "class AuditedBase\|class TenantMixin" backend/app/models/base.py

# 3-5. alembic head
cd backend && alembic current
```

**보고할 것**
- `users` 테이블에 부서 관련 컬럼이 이미 있는지
- 현재 권한 검사가 어디서 이뤄지는지 (엔드포인트별 의존성? 미들웨어?)
- `owner_name` 값 분포 — 팀 이름·복수 인물이 실제로 몇 건인지
- 신규 테이블에 `AuditedBase`를 쓰면 되는지 (ADR-0030 복합 FK 격리 적용 대상)

**실측이 ADR-0031 전제와 어긋나면 코드를 맞추지 말고 보고할 것.**

## 4. 구현 원칙

- **ADR-0020 준수.** 서비스 클래스·패턴 금지. 직접 함수와 명시적 분기만
- **ADR-0025 준수.** 테넌트 필터를 수동으로 걸지 않는다. `AuditedBase` 상속으로 자동 격리
- **ADR-0030 준수.** 신규 테이블 간 FK는 복합 FK로 테넌트 격리를 DB가 보장하게 할 것
- 기존 `control_resolver.py`의 `_resolve_layer` 방식을 참고하되 복제하지 말 것.
  배정 해석(기본값+예외)이 유사 구조이나, 공용화할지 별도 작성할지는 판단 후 보고

## 5. API

CRUD 계약은 **기존 RCM API와 동일한 규약**을 따른다.
`docs/api/rcm-hierarchy-contract.md`를 참조할 것.

- 목록 응답 봉투: `{"items": [...], "total": int, "skip": int, "limit": int}`
- 배정 조회 응답에 출처 표시 (프로세스 기본값 / 통제별 지정)
- 에러: 404 `{"detail": "..."}`, 409 사용자 노출 가능한 한국어 메시지
- code 중복 등 검증은 핸들러에서 명시적으로 수행 (DB 제약에만 의존하지 않음)

**`external_auditor`는 모든 생성·수정 API에서 거부되어야 한다.**

## 6. 검증 조건

1. 한 사용자가 여러 부서에 소속 가능
2. 사용자당 주 소속이 정확히 하나임이 보장됨 (둘 이상 설정 시 거부)
3. 한 사용자가 여러 부서의 책임자로 지정 가능
4. **같은 사용자가 통제 A에서 `control_owner`, 통제 B에서 `assessor`로 배정 가능**
5. 프로세스 기본값 변경 시 개별 지정 없는 통제에 자동 반영
6. 통제별 예외 지정이 프로세스 기본값보다 우선
7. 배정 조회 응답에서 기본값 유래와 개별 지정이 구분됨
8. `control_owner` = `assessor` 배정 시 사유 없으면 거부, 사유 있으면 저장 + 이력 기록
9. 정책 토글을 금지로 전환하면 해당 조합 배정이 409로 거부
10. `dept_approver`가 통제책임자의 주 소속 부서 책임자로 유도됨
11. 통제별로 `dept_approver`를 개별 지정하면 유도값보다 우선
12. `external_auditor` 계정으로 생성·수정 API 호출 시 거부
13. 다른 테넌트의 부서·배정에 접근 불가 (postgres에서 확인)
14. 전체 pytest 통과

**4번과 8번이 핵심이다.**
4번은 §2.3(통제 단위 배정)이, 8번은 §2.5(막지 않고 기록)가 구현됐는지 본다.
4번이 없으면 사람 단위 RBAC으로 만들어도 통과한다.

**13번 주의** — sqlite는 FK를 강제하지 않는다. 로컬 통과를 격리 검증으로
인정하지 않는다. postgres에서 확인하고, sqlite에서 검증 불가하면 그 사실을 명시할 것.

## 7. 커밋 분리

1. `feat(db): 부서·사용자소속 테이블 추가 (3-1, ADR-0031 §2.8)`
2. `feat(db): 역할 배정·정책 테이블 추가 (3-1, ADR-0031 §2.2~2.4)`
3. `feat(org): 부서 CRUD API`
