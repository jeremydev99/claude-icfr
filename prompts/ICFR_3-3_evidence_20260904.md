# 3-3: 증빙 관리 (ADR-0032 §2.7)

작성일: 2026-09-04
근거 ADR: ADR-0032(평가 회차·워크플로) §2.7·§2.9, ADR-0031(역할·권한), ADR-0030(테넌트 소유권), ADR-0025(자동 격리), ADR-0020(제로 추상화)
선행: 3-1(부서·역할 배정), 3-2(평가 회차·워크플로) — 완료, 운영 배포됨(d67af48)

## 0. 이 작업의 성격

**증빙은 감사 증거물이다.** 다른 데이터와 다르게 다뤄야 한다.

- 지워지면 안 된다. 삭제해도 파일과 이력이 남는다
- 누가 언제 올렸다가 지웠는지가 감사에서 실제로 묻는 질문이다
- 보존기간이 법정 최소 5년이다(ADR-0032 §2.9)

구현 편의를 위해 이 성질을 훼손하지 않는다.

## 1. 범위

**포함**
- 증빙 업로드·조회·삭제 (통제 × 회차)
- MinIO 저장 및 테넌트 격리
- 삭제 이력 보존
- 회차 상태에 따른 편집 권한
- 테넌트 정책: 증빙 편집 토글, 보존기간

**제외**
- 아카이브 → 별도 ADR
- 파일 내용 검증(바이러스 스캔, 형식 검사) → 별건
- 미리보기·썸네일 → 별건

## 2. 설계 확정 사항

### 2.1 증빙은 통제 × 회차에 붙는다

통제에만 붙는 것이 아니다. 같은 통제라도 회차가 다르면 다른 증빙이다.

- 하나의 통제 × 회차에 증빙 여러 개가 붙는다
- **여러 사용자가 각자 올릴 수 있다.** 업로더가 기록된다
- 3-2의 활동 기록과의 관계를 판단할 것 — 증빙이 활동에 붙는지,
  통제×회차에 직접 붙는지. **근거와 함께 보고할 것**

### 2.2 MinIO 격리는 경로 분리

**버킷을 테넌트별로 나누지 않는다. 한 버킷 안에서 경로로 나눈다.**

```
{tenant_id}/cycles/{cycle_id}/controls/{control_id}/{evidence_id}
```

**기각한 대안 — 버킷 분리.** 테넌트 온보딩마다 버킷 생성이 필요하고,
고객사 서버 설치 시 MinIO 설정 절차가 늘어난다.

**주의 — 경로 분리는 DB의 복합 FK 같은 구조적 보장이 없다.**
애플리케이션이 경로를 잘못 만들면 다른 테넌트 파일에 접근할 수 있다.

따라서 **경로 생성을 한 곳에서만 한다.** 경로 문자열을 조립하는 함수를 하나 두고,
그 함수만 사용한다. 다른 곳에서 문자열을 이어붙이지 않는다.
tenant_id는 그 함수가 컨텍스트에서 직접 가져오며, 호출자가 넘기지 않는다
(호출자가 넘기면 잘못된 값을 넘길 수 있다).

**다운로드 시에도 경로로 판정하지 않는다.** DB에서 증빙 레코드를 조회하고
(ADR-0025 자동 격리가 걸림), 그 레코드의 경로로 파일을 읽는다.
경로를 파라미터로 받아 그대로 읽는 엔드포인트를 만들지 않는다.

### 2.3 파일명은 내부 식별자로 저장한다

MinIO에는 내부 식별자로 저장하고, **원본 파일명은 DB에 둔다.**

- 한글 파일명, 중복 이름, 경로 조작 시도가 한 번에 해결된다
- 다운로드 시 `Content-Disposition`으로 원본명을 내려준다. 사용자는 차이를 느끼지 않는다

### 2.4 삭제는 파일까지 남긴다

**DB 레코드도, MinIO 파일도 지우지 않는다.**

- 삭제 표시만 하고 조회에서 제외한다
- "누가 언제 올렸다가 삭제했는지"와 **그 파일 내용까지** 남는다
- 레코드만 남기고 파일을 지우면 "그때 지운 게 뭐였나"에 답할 수 없다.
  보존기간이 5년 이상이므로 파일도 그 기간을 따른다

삭제 이력에 남길 것: 업로더, 업로드 시각, 삭제자, 삭제 시각, 삭제 사유(선택).

### 2.5 편집 권한은 회차 상태에 달려 있다

| 회차 상태 | 통제책임자 | `icfr_manager` |
|---|---|---|
| 진행 중 | 업로드·삭제 가능(기본) | 가능 |
| 마감됨 | **불가** | 승인 하에 가능 |
| 최종승인됨 | **불가** | 승인 하에 가능 |

- 진행 중 편집 허용 여부는 **테넌트 정책 토글**로 제어. 기본은 허용
- 권한 판정은 **통제 단위**다. 3-1의 `role_resolver`를 사용할 것
- 마감 후 관리자 편집은 그 사실이 이력에 남아야 한다

**`external_auditor`는 조회만 가능하다.** 업로드·삭제 모두 거부.

### 2.6 크기 상한을 두지 않는다

원본이 보존되어야 제도 운영 취지에 맞는다(ADR-0032 §2.7).

**다만 무제한 업로드는 운영 위험이다.** 다음을 판단하고 보고할 것.

- 스트리밍 업로드인지 메모리 적재인지. 대용량 파일이 백엔드 메모리를 소진하지 않아야 한다
- `/data` 잔여 용량을 확인할 수단이 있는지. 디스크가 차면 서비스가 멈춘다
- 상한을 두지 않되 **경고 임계치**를 둘지

상한을 코드에 하드코딩하지 말 것. 필요하면 정책 설정으로.

### 2.7 보존기간

- 테넌트 정책에 보존기간을 둔다
- **최소 5년을 시스템이 강제한다.** 5년 미만 설정 불가
  근거: 내부회계관리제도 업무지침 — 회계정보 및 관련 문서 5년 보관
- 기본값은 영구 보존
- **이번에는 설정값만 저장한다.** 실제 만료 삭제 처리는 아카이브 설계와 함께 다룬다

```bash
# 3-1. MinIO 현재 사용 방식 — 이미 붙어 있는 코드가 있는지

# 3-4. 3-2 활동 기록 구조 — 증빙을 어디에 붙일지 판단 근거

# 3-6. alembic head

```

**보고할 것**
- MinIO 클라이언트가 이미 있는지, 없으면 무엇을 쓸지 + 근거
- 증빙을 활동에 붙일지 통제×회차에 직접 붙일지 + 근거
- 스트리밍 업로드 가능 여부
- 보존기간을 `tenant_policies`에 두는 방식 (3-2 회계연도 시작월과 같은 방식인지)

**실측이 ADR-0032 §2.7 전제와 어긋나면 코드를 맞추지 말고 보고할 것.**

## 5. 검증 조건

1. 같은 통제 × 회차에 증빙 여러 개 업로드 가능, 업로더가 각각 기록됨
2. 다른 회차에 같은 통제의 증빙을 올리면 별개로 관리됨
3. 한글 파일명 업로드 → 저장 성공, 다운로드 시 원본명으로 내려옴
4. 같은 이름 파일 중복 업로드 → 둘 다 보존됨
5. **삭제 후 조회에서 제외되지만, 이력 조회 시 업로더·업로드시각·삭제자·삭제시각이 나옴**
6. **삭제된 증빙의 MinIO 파일이 여전히 존재함**
7. 마감된 회차에 통제책임자가 업로드 시도 → 거부
8. 마감된 회차에 `icfr_manager`가 업로드 → 성공, 이력에 기록됨
9. 정책 토글을 금지로 전환 → 진행 중 회차에서도 통제책임자 업로드 거부
10. `external_auditor` 업로드·삭제 시도 → 거부. 조회는 가능
11. 통제 A의 통제책임자가 통제 B의 증빙을 올리려 하면 거부 (통제 단위 권한)
12. 보존기간 5년 미만 설정 시도 → 거부
13. **다른 테넌트의 증빙 파일에 접근 불가** — DB 조회 단계에서 차단됨을 확인
14. MinIO 경로에 tenant_id가 포함됨
15. 전체 pytest 통과, xfail 1건 유지

**5·6번이 핵심이다.** §2.4(파일까지 남긴다)가 구현됐는지 본다.
6번이 없으면 파일을 지우는 구현도 5번을 통과한다.

**13번 주의** — 경로 격리는 DB 같은 구조적 보장이 없다.
"경로를 조작해도 못 읽는다"가 아니라 "DB 조회에서 걸러진다"를 검증할 것.
