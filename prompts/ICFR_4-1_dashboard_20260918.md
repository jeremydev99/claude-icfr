# 4-1: 대시보드 (개발 현황판 + RCM 실데이터)

작성일: 2026-09-18
관련: ADR-0031(역할·권한), ADR-0032(평가 회차), 13.9-35 해소분
선행: 3-1·3-2·3-3 완료, 운영 배포됨

---

## 0. 이 작업의 목적 — 개발 현황판이 먼저다

**대시보드를 "지금 어디까지 됐는지 한눈에 보는 화면"으로 먼저 만든다.**

현재 사이드바 메뉴 9개 중 RCM을 제외하면 전부 "Phase 1에서 구현 예정"이다.
어디까지 됐는지 화면으로는 알 수 없고 문서를 열어야 한다.

- 준비 중인 모듈은 **자리만 차지하게** 두고 회색 + "준비중" 배지로 표시한다
- 실데이터가 있는 RCM만 제대로 붙인다
- 준비 중 카드의 UI는 나중에 실제 화면으로 대체되므로 공들이지 않는다

**0건도 0으로 보여준다.** "준비중"으로 가리지 않는다.
배정 0건, 회차 0건이 보이는 것 자체가 현황이고, 다음에 무엇을 해야 하는지를 드러낸다.

## 1. 범위

**포함**
- 대시보드 캔버스 — 모든 모듈 현황을 한 화면에서 조회
- 모듈 카드 클릭 → 해당 모듈 메뉴로 이동
- 준비 중 모듈: 회색 + "준비중" 배지
- RCM 카드: 실데이터 집계 + 드롭다운 펼침 + 항목 클릭 시 RCM 메뉴 이동
- 위를 위한 백엔드 집계 API

**제외 — 스키마 변경이 필요해 별건으로 둔다**
- 통제 비고란 → `baseline_controls`에 비고 컬럼이 없다. RCM 작업 시 추가
- 중요도 세분화 → 현재 `is_key_control` 2단계뿐. 지금 단계에서 불필요
- 기간 조회 → 평가 회차 데이터가 0건이라 조회할 과거가 없다.
  회차가 쌓인 뒤 붙인다

## 2. RCM 카드 — 지금 나오는 것과 0으로 나오는 것

### 2.1 실제 숫자가 나오는 집계

`baseline_controls` 실측 기준(운영 93건). 전부 resolver 경유로 조회할 것.

| 구분 | 컬럼 | 비고 |
|---|---|---|
| 핵심통제 여부 | `is_key_control` | 핵심 / 비핵심 |
| 평가주기 | `assessment_frequency` | 연 91 / 분기 1 / 월 1 (운영 실측) |
| 프로세스별 | `risk_id` → 상위 체인 | 프로세스 8개 |
| 예방/적발 | `preventive_detective` | |
| 자동/수동 | `auto_manual` | |
| 통제활동 유형 | `activity_*` 6종 | 승인·검증·물리적통제·마스터데이터·대사·감독 |
| IPE 관련 | `ipe_relevant` | |

### 2.2 구조는 만들되 지금은 0으로 나오는 것

| 구분 | 출처 | 현재 |
|---|---|---|
| 통제 조직별 | `control_owner` 배정 → 주 소속 부서 | 배정 0건 → "미배정 93건" |
| 진행 현황 | 평가 회차·활동 | 회차 0건 → 전부 0 |

**통제 조직은 새 분류 체계를 만들지 않는다.**
3-1에서 만든 `departments` + 역할 배정을 쓴다.
통제의 `control_owner`가 배정되면 그 사람의 주 소속 부서가 조직이다.
`role_resolver`를 사용할 것. 판정 로직을 복제하지 말 것.

진행 현황 항목: 통제활동 개수 / 시점별 진행 의무 개수 / 완료·미완료 건수.
회차가 생기면 자동으로 채워지는 구조로 만들 것.

## 3. 동작

### 3.1 드롭다운 펼침

각 집계 항목을 펼치면 그 섹터의 **전체 항목 목록**이 보인다.
항목을 클릭하면 RCM 메뉴로 이동하되, **그 필터가 적용된 상태로 이동**할 것.

예: "핵심통제 93건" 펼침 → 통제 목록 → 항목 클릭 → RCM 관리에서 해당 통제

RCM 화면에 이미 필터 기능이 있다(프로세스·위험수준·주기·자동수동·예방적발·어서션).
쿼리 파라미터로 필터 상태를 전달할 수 있는지 확인하고, 없으면 그 방식을 설계할 것.

### 3.2 모듈 카드 이동

준비 중 카드도 클릭하면 해당 메뉴로 이동한다(빈 화면이 뜬다).
이동 자체가 막히면 "왜 안 눌리지"가 되므로 막지 않는다.

## 4. 준비 중 모듈 표시

사이드바 메뉴 기준으로 카드를 만든다.

| 모듈 | 상태 |
|---|---|
| RCM 관리 | 실데이터 |
| 일정관리 / Scoping / EUC / IUC / Test / 개선계획 / 증빙 관리 / Report / 담당자·권한 / 메일발송 | 준비중 |

**증빙 관리와 담당자·권한은 백엔드가 있으나 화면이 없다.**
이 둘은 "준비중"이되 백엔드 상태를 구분해서 표시할지 판단하고 보고할 것.
구분이 필요하면 배지를 나누고, 과하면 동일 처리한다.

## 5. 사전 실측 (STEP 0)

```bash
# 5-1. RCM 화면 필터가 URL 파라미터를 받는지
grep -rn "searchParams\|useSearchParams\|URLSearchParams" frontend/src/features/rcm/ | head -20

# 5-2. 기존 대시보드 화면 상태
find frontend/src -path "*dashboard*" -o -name "*Dashboard*" | head -10

# 5-3. 사이드바 메뉴 정의 위치
grep -rn "RCM 관리\|Scoping\|개선계획" frontend/src --include=*.tsx --include=*.ts | head -10

# 5-4. resolver 집계 함수가 있는지
grep -n "^def " backend/app/services/control_resolver.py

# 5-5. role_resolver 인터페이스
grep -n "^def " backend/app/services/role_resolver.py
```

**보고할 것**
- RCM 필터가 URL 파라미터를 받는지. 안 받으면 어떻게 붙일지
- 집계를 백엔드 API로 낼지, 기존 목록 API 결과를 프론트에서 집계할지 + 근거
  (93건이면 프론트 집계도 가능하나, 고객사 통제 수백 건이면 달라진다)
- 증빙·담당자권한 카드 구분 표시 여부 판단

## 6. 구현 원칙

- **ADR-0020 준수.** 서비스 클래스·패턴 금지
- **ADR-0025 준수.** 테넌트 필터 수동 금지
- 집계는 resolver 경유. baseline 테이블 직접 조회 금지
- `external_auditor`는 대시보드 **조회 가능**. 대시보드에 쓰기 동작은 없다
- 프론트는 `can_write` 를 게이트로 쓴다(직접 역할 판정 금지)

## 7. 검증 조건

1. 대시보드에서 RCM 집계가 운영 실데이터와 일치 (통제 93, 프로세스 8)
2. 평가주기 분포가 연 91 / 분기 1 / 월 1 로 표시
3. 조직별 집계가 "미배정 93건"으로 표시 (0을 가리지 않음)
4. 진행 현황이 전부 0으로 표시 (회차 0건)
5. 드롭다운 펼침 → 전체 항목 목록 표시
6. 항목 클릭 → RCM 메뉴로 이동, 해당 필터 적용 상태
7. 준비 중 카드 클릭 → 해당 메뉴로 이동 (빈 화면)
8. `external_auditor` 계정으로 대시보드 조회 가능
9. 전체 pytest 통과. **2회 반복 실행으로 재현성 확인**

**3·4번이 이 작업의 성격을 결정한다.**
0을 "준비중"으로 가리면 현황판 목적이 무너진다.
