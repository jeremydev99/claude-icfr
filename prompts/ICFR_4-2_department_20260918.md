# 4-2: 부서 관리 화면

작성일: 2026-09-18
근거 ADR: ADR-0031(역할·권한 모델) §2.8, ADR-0025(자동 격리), ADR-0020(제로 추상화)
선행: 3-1(부서·역할 배정 API) 완료, 4-1(대시보드) 완료
API: 이미 존재. 화면만 없다

---

## 0. 왜 이것부터인가

대시보드가 "통제 조직별 — 미배정 93건"을 보여준다.
그것을 푸는 순서가 **부서 → 소속 → 역할 배정**이고, 지금 셋 다 화면이 없다.

부서가 생기면 대시보드에서 유일하게 0인 축이 실제 숫자로 바뀐다.

## 1. 범위

**포함**
- 부서 목록·생성·수정·삭제
- 부서별 소속 인원 관리 (부서 화면 안에서)
- 부서 책임자 지정
- 관리자 기능 > 부서 관리 메뉴에 연결

**제외**
- 역할 배정 화면 → 별건(4-3)
- 계층 구조 UI → `parent_id`는 컬럼만 있고 평면으로 운영한다(ADR-0031 §2.8)
- 인사시스템 연동 → `external_code`는 컬럼만 있고 현재 미사용

## 2. 설계 확정 사항

### 2.1 소속은 부서 화면 안에서 관리한다

별도 "소속 관리" 화면을 만들지 않는다.

**근거** — "자금팀에 누가 있나"가 부서를 보는 자연스러운 질문이다.
화면을 하나 더 만들면 메뉴가 늘고, 부서와 소속을 오가야 한다.

부서를 선택하면 그 부서의 인원이 보이고, 거기서 추가·제거한다.

### 2.2 주 소속은 정확히 하나다

한 사람이 여러 부서에 속할 수 있으나 주 소속은 하나다(ADR-0031 §2.2).
DB에 부분 유니크 제약이 걸려 있다.

**UI에서 이 규칙이 보여야 한다.**
- 주 소속 여부를 표시할 것
- 이미 주 소속이 있는 사람을 다른 부서의 주 소속으로 지정하면 어떻게 되는지
  판단하고 보고할 것 — 기존 주 소속을 옮길지, 거부할지
- 서버가 거부하면(409) 그 문구를 사용자가 이해할 수 있게 표시할 것

### 2.3 부서 책임자

`manager_id`. **한 사람이 여러 부서의 책임자가 될 수 있다**(ADR-0031 §2.8).
본부장이 팀장 퇴사 시 겸임하는 경우가 실재한다. 막지 말 것.

책임자는 그 부서 소속이 아니어도 된다 — 본부장이 팀을 겸임하면
소속은 본부에 있다. 소속 목록과 책임자를 별개로 다룰 것.

### 2.4 삭제

부서에 소속 인원이 있거나 역할 배정에서 참조 중이면 어떻게 되는지
API 동작을 확인하고, 그에 맞게 UI를 만들 것.

**추정하지 말 것.** 실제 응답을 확인해서 보고할 것.
소프트 삭제인지 거부인지에 따라 화면이 달라진다.

### 2.5 권한

부서 관리는 `icfr_manager` 전용이다.

**메뉴 노출·버튼 활성을 `can_write`로 판정하지 말 것.**
`can_write`는 `external_auditor` 판정이지 `icfr_manager` 판정이 아니다.
`tenant_roles`를 봐야 한다. 이 구분을 코드 주석에 남길 것.

권한이 없는 사용자에게 어떻게 보일지 판단하고 보고할 것 —
메뉴를 감출지, 보이되 읽기 전용으로 둘지.

## 3. 사전 실측 (STEP 0)

```bash
# 3-1. 부서 API 실제 스키마
grep -n -A20 "departments" backend/app/schemas/org.py | head -40

# 3-2. 소속(memberships) API
grep -n -A15 "membership" backend/app/api/org.py | head -30

# 3-3. 부서 삭제 시 동작 — 참조가 있으면?
grep -n -B5 -A15 "def delete_department\|departments/{" backend/app/api/org.py

# 3-4. 사용자 목록 API — 소속 추가 시 사람을 고를 수단
grep -n "def list_users\|/users" backend/app/api/user_mgmt.py | head

# 3-5. 기존 관리자 화면 패턴 — 담당자/권한 화면 구조
find frontend/src -path "*user*" -name "*.tsx" | head -10

# 3-6. 대시보드 조직별 집계가 무엇을 읽는지
grep -n "organization\|department" backend/app/api/rcm.py | head
```

**보고할 것**
- 부서 삭제 시 참조가 있으면 어떻게 되는지 (실제 응답)
- 주 소속 중복 지정 시 서버 응답 (409 문구 원문)
- 사용자 목록 API가 있는지, 없으면 소속 추가 UI를 어떻게 만들지
- 기존 관리자 화면(담당자/권한)의 패턴을 따를 수 있는지

**실측이 ADR-0031 §2.8 전제와 어긋나면 코드를 맞추지 말고 보고할 것.**

## 4. 구현 원칙

- **ADR-0020 준수.** 서비스 클래스·패턴 금지
- **ADR-0025 준수.** 테넌트 필터 수동 금지
- 기존 관리자 화면 패턴을 따를 것. 새 패턴을 만들지 말 것
- API는 이미 있다. **백엔드를 고쳐야 한다면 그 사실부터 보고할 것** —
  화면을 만들다 API가 부족해 고치는 건 정상이나, 조용히 고치지 말 것

## 5. 검증 조건

1. 부서 생성 → 목록에 표시
2. 부서 수정·삭제 동작
3. 부서에 인원 추가 → 소속 목록에 표시
4. **주 소속이 이미 있는 사람을 다른 부서 주 소속으로 지정 → 정의한 동작대로**
5. 한 사람을 여러 부서 책임자로 지정 → 성공
6. 부서 책임자가 그 부서 소속이 아니어도 지정 가능
7. `icfr_manager`가 아닌 계정에서 정의한 대로 동작 (감춤 또는 읽기전용)
8. `external_auditor` 계정에서 쓰기 동작 전부 거부
9. **부서 생성 + 통제에 control_owner 배정 후 대시보드 조직별 집계에 반영**
   (역할 배정 화면이 없으므로 API로 배정해서 확인할 것)
10. 전체 pytest 통과. **2회 반복 실행으로 재현성 확인**

**4번과 9번이 핵심이다.**
4번은 §2.2가 UI에서 지켜지는지, 9번은 이 작업이 대시보드의 0을 실제로 푸는지 본다.
