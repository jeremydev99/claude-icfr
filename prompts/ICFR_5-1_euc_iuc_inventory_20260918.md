## 0. 첫 커밋 — ADR-0033 정정

구현 전에 ADR부터 고친다. **초안 서술을 덮어쓰지 말고 정정 이력으로 남길 것.**
아래 문안을 해당 절에 그대로 추가한다. 별도 docs 커밋으로 분리한다.

### §2.1에 추가

> **2026-09-18 정정 — EUC 파일을 독립 대상으로 둔다.**
>
> 초안은 "데이터는 통제 중심 하나"로 정보 항목에 EUC 필드를 통합했다.
> 이 구조는 **엑셀 파일 하나를 여러 통제가 공유하는 경우**를 표현하지 못한다.
> 현재 샘플 8건은 전부 1:1이라 드러나지 않았으나, 향후 공유가 발생할 수 있으므로 열어 둔다.
>
> 통제 중심으로 두면 공유 파일이 통제마다 중복 등록되고,
> §2.5의 EUC 통제 4종도 같은 파일에 대해 중복으로 붙어 중복 평가된다.
>
> 정정된 구조:
> ```
> RCM 통제 ──1:N── 정보 항목(IUC) ──N:1── EUC 파일 ── EUC 통제 4종
> ```
> - 정보 항목은 RCM 통제에 딸린다. 통제가 쓰는 정보를 기술한다(IUC 관점)
> - 정보 Type이 EUC인 정보 항목은 EUC 파일을 참조한다
> - 여러 정보 항목(= 여러 통제)이 같은 EUC 파일을 참조할 수 있다
>
> 화면은 여전히 둘이다. EUC 화면은 파일 중심, IUC 화면은 정보 항목(통제) 중심.
> 저장소를 갈라놓는 것이 아니라 **서로 다른 대상 둘을 연결하는 것**이다.

### §2.2에 추가

> **2026-09-18 정정 — 입력 위치를 성질에 맞춘다.**
>
> | 값 | 입력 위치 | 근거 |
> |---|---|---|
> | 복잡도 | EUC 파일 | 매크로·수식 구조는 파일 자체의 성질이다. 어느 통제가 쓰든 같다 |
> | 중요성 | 정보 항목 | 같은 파일도 쓰는 통제에 따라 재무보고 영향이 다르다 |
> | 파일 중요성 | **자동 산출** — 연결된 정보 항목 중 최고값 | 한 곳이라도 중요하게 쓰이면 그 파일은 중요하다 |
> | 위험 등급 | **자동 산출** — 복잡도 × 파일 중요성 | |
> | 통제 식별 여부 | **자동 산출** — 위험 등급 ≥ 임계값 | |
>
> 사람은 재료 두 가지(파일 복잡도, 정보별 중요성)만 넣는다.
> 파일 단위 중요성·위험 등급·통제 식별 여부는 시스템이 산출한다.
> "한 곳에서만 입력"(§2.2 초안) 원칙은 유지된다 — 각 값은 입력처가 하나다.
>
> 여기서 "파일에 입력"은 ICFR 시스템 안의 EUC 파일 항목을 말한다.
> 실제 엑셀 파일 자체에는 아무것도 기록하지 않는다.

### §2.5에 추가

> **2026-09-18 정정 — EUC 통제 4종은 EUC 파일에 붙는다.**
> 정보 항목이나 RCM 통제에 붙지 않는다. 파일 하나에 통제 4종 한 세트다.

### §3·§4 갱신

- §3 영향 범위의 "정보 항목 (통제×정보, EUC·IUC 필드 통합)"을
  "정보 항목(통제에 딸림) + EUC 파일(독립) + 둘의 참조 관계"로 정정
- §4 검증 조건에 추가
  - 한 EUC 파일을 두 통제의 정보 항목이 참조 → EUC 파일은 1건
  - 파일 중요성 = 연결된 정보 항목 중요성의 최고값
  - 정보 항목 하나의 중요성을 올리면 파일 위험 등급이 따라 바뀜

## 2. 설계 확정 사항

### 2.1 값 상수 — 한 곳에 정의

대시보드 0건 미표시(ClaudeICFR.md 13.9-40)의 교훈이다.
값 집합이 상수로 없으면 데이터에 있는 값만 나열하게 된다.

| 상수 | 값 | 비고 |
|---|---|---|
| 정보 Type | `EUC information` | 현재 원천 양식에 이 값만 있다. **확장 가능하게** 둘 것(ADR-0033 §2.7) |
| EUC 파일변경주기 | E / D / W / M / Q / S / A / 건별 | **EUC 전용 상수.** RCM 수행주기(O/D/W/M/Q/A)를 재사용하지 말 것 — E·S·건별이 조용히 빠진다(13.9-43) |
| 복잡도 | 단순 기록 / 수식 재가공 / 매크로·링크·모델 | ADR-0033 §2.3 |
| 중요성 | H / M / L | 원천 IUC 양식 값 |
| 위험 등급 | Low / Moderate / High | 원천 EUC 양식 값 |

값의 표기(코드값·라벨)는 원천 양식과 대조해서 정할 것. 원천이 `Low`·`moderate`처럼
대소문자가 섞여 있다. 코드값은 하나로 정규화하되, **어떻게 정규화했는지 보고할 것.**

### 2.2 위험 등급 산출 — 초기값

복잡도 3단계 × 중요성 3단계 매트릭스로 산출한다.

초기 매트릭스를 아래로 둔다. **근거가 있는 표준값이 아니라 초기값이다.**
한 곳에 정의하고, 초기값이라는 사실과 출처(ADR-0033 §2.3, 국내외 표준의 2축 모델)를
코드 주석에 남길 것.

| 복잡도 \ 중요성 | L | M | H |
|---|---|---|---|
| 단순 기록 | Low | Low | Moderate |
| 수식 재가공 | Low | Moderate | High |
| 매크로·링크·모델 | Moderate | High | High |

**통제 식별 임계값은 `tenant_policies`에 둔다.** 기본 Moderate(원천 양식 수식
`=IF(OR(위험평가="moderate",위험평가="high"),"통제식별","")`과 일치).
하드코딩하지 말 것 — 회사·감사인 협의로 조정된다.

### 2.3 시드 — 원천에 없는 값을 지어내지 말 것

원천 양식에는 **복잡도가 없다.** `Macro 포함여부`(8건 모두 No)만 있다.
매크로가 없다는 것만으로 "단순 기록"인지 "수식 재가공"인지 알 수 없다.

**복잡도를 추정해서 채우지 말 것.** 처리 방식을 판단하고 보고할 것. 예:
- 복잡도를 미평가(NULL)로 두고, 위험 등급도 "미평가"로 표시
- 원천의 `위험평가`(Low) 값은 원천 참고값으로 따로 보존

원천 양식은 위험평가를 직접 적었고, 우리 모델은 산출한다. 이 차이를
시드에서 어떻게 처리했는지가 보고에 드러나야 한다.

IUC 시트는 254행이나 데이터는 8행이다. **No 열을 기준으로 끊을 것**(13.9-43).
EUC Control Test 시트는 `#REF!`가 섞인 예시 양식이므로 시드 대상이 아니다.
저장소 열은 "추후 사이냅소프트 작성"이라 비어 있다 — 그 문구를 값으로 넣지 말 것.

### 2.4 "전부 Low"는 그대로 보여준다

원천 8건이 전부 Low·L이라 임계값 기준으로 **통제 식별 대상이 0건**이다.
화면과 대시보드에 **0건으로 정직하게** 표시한다. 숨기거나 준비중으로 가리지 않는다.
실제 평가 결과인지는 마스터가 별도 확인한다(13.9-44).

### 2.5 권한 — require_write로 기본 처리하지 말 것

오늘 두 번 반복된 결함이다(13.9-35, 13.9-41). 기존 가드를 그대로 쓰면
의도보다 넓게 열린다.

**누가 쓸 수 있는지 명시적으로 정하고, 구현 전에 보고할 것.** 권장안:

| 대상 | 쓰기 권한 |
|---|---|
| 정보 항목 | `icfr_manager` + 그 통제의 `control_owner`·`assessor` (통제 단위, `role_resolver`) |
| EUC 파일 | `icfr_manager` + 그 파일을 참조하는 통제 중 하나의 `control_owner` |
| 임계값 정책 | `icfr_manager` |

`external_auditor`는 조회만. 조회는 전원 가능.
프론트 게이트는 `can_write`로 판정하지 말 것 — `tenant_roles`를 봐야 한다.

## 4. 구현 원칙

- **ADR-0020 준수.** 서비스 클래스·패턴 금지
- **ADR-0025 준수.** 테넌트 필터 수동 금지. 신규 테이블 전부 `AuditedBase`
- **ADR-0030 준수.** 정보 항목→EUC 파일, 정보 항목→통제 FK는 복합 FK로 테넌트 격리
- **소프트 삭제 + 유니크는 처음부터 부분 유니크(`WHERE NOT is_deleted`)로.**
  오늘 두 테이블에서 사후에 고쳤다(13.9-35 ④, 13.9-42). 같은 것을 또 만들지 말 것
- 파일 중요성·위험 등급은 **저장하지 않고 조회 시 산출**할지, 저장할지 판단해서 보고할 것.
  ADR-0029 §2.2(유도 가능한 값은 저장하지 않는다)를 참고하되,
  목록 정렬·필터 성능 문제가 있으면 근거와 함께 보고
- 기존 화면 패턴(features/users, 부서 관리)을 따를 것

## 5. 검증 조건

1. 시드 후 정보 항목 8건, EUC 파일 8건, 1:1 연결
2. **한 EUC 파일을 두 통제의 정보 항목이 참조 → EUC 파일 1건** (테스트로 공유 상황을 만들 것)
3. **파일 중요성 = 연결된 정보 항목 중 최고값.** 하나를 L→H로 바꾸면 파일 중요성·위험 등급이 따라 바뀜
4. 복잡도·중요성 입력 → 위험 등급이 §2.2 매트릭스대로 산출
5. 임계값을 High로 바꾸면 통제 식별 대상이 달라짐 (하드코딩 아님)
6. 파일변경주기 선택지에 E·S·건별이 나타남 (RCM 상수 재사용 아님)
7. 정보 Type·중요성·위험 등급 값 목록이 상수에서 오고, 0건 값도 화면·대시보드에 표시
8. 원천 "전부 Low" 상태가 대시보드에 식별 대상 0건으로 표시
9. §2.5 권한대로 동작 — 통제 A의 `control_owner`가 통제 B의 정보 항목 수정 시 거부
10. `external_auditor` 쓰기 전부 거부
11. 삭제 후 같은 키로 재생성 가능 (부분 유니크)
12. 다른 테넌트의 정보 항목·EUC 파일 접근 불가 (postgres에서 확인)
13. 전체 pytest 통과. **2회 반복 실행으로 재현성 확인**

**2·3번이 이번 정정의 핵심이다.**
2번이 없으면 통제 중심 구조로 만들어도 통과한다. 3번은 파일 중요성 자동 산출이
실제로 동작하는지 본다.

**12번 주의** — sqlite는 FK를 강제하지 않는다. postgres에서 확인할 것.
