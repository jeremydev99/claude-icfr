# ADR-0027: RCM Baseline / Overlay 구조 — 2단계 근간 설계

- **상태**: 채택 (Accepted)
- **일자**: 2026-06-15
- **결정자**: 마스터(CFO/창업자)
- **관련 ADR**: ADR-0025(플랫폼 근간 — baseline+overlay+멀티테넌시), ADR-0026(멀티테넌시 1단계), ADR-0020(제로 추상화)
- **성격**: ADR-0025의 baseline/overlay를 RCM에 실제 구현하는 근간 설계. 후속 구현(2-A~2-C)은 이 문서 위에 단계적으로 얹는다.

---

## Context

ADR-0025에서 "Basic-perfect baseline + 회사별 overlay(비채택/추가/변형)" 구조를 결정했고, ADR-0026에서 멀티테넌시 1단계(tenant_id 전면 + 자동 격리)를 구현했다. 이제 그 구조를 **RCM(Process→SubProcess→Risk→Control + RiskCategory)**에 실제로 적용한다.

현재 RCM은 baseline과 회사 데이터가 분리되지 않은 단일 구조이며, 모든 `code`가 **글로벌 unique**다. 이는 멀티테넌시·baseline/overlay와 정면 충돌한다 — 두 번째 회사가 같은 code를 쓰거나 baseline을 변형하는 순간 unique 위반으로 저장이 불가능하다.

목표: **모든 커스터마이징 case에 대응 가능한** baseline/overlay 구조. 외부 판매 기준의 완벽성을 추구한다.

---

## Decision

### 1. baseline 범위 — 계층 전체

Process·SubProcess·Risk·Control·RiskCategory **전 계층**을 baseline으로 제공한다. 표준 프로세스 분류까지 Basic-perfect의 일부다. 표준이 있어야 그로부터의 변형이 의미를 가진다. 회사는 각 계층에서 비채택/변형/추가할 수 있다.

### 2. 방식 A — baseline 테이블 / instance 테이블 완전 분리

각 계층을 두 테이블로 분리한다 (Control 예시, 전 계층 동일 패턴):

**baseline 테이블** (표준, tenant 무관)
- 예: `baseline_controls` — 표준 통제. `tenant_id` 없음(전역). Basic-perfect의 그릇.
- `code` 전역 unique (표준이므로 하나뿐).

**instance 테이블** (회사별 결정)
- 예: `control_instances` — `tenant_id`, `baseline_control_id`(nullable), `action`, override 필드들(nullable).
- `(tenant_id, code)` 복합 unique (회사 안에서만 유일).

**방식 B(단일 테이블 + baseline 플래그)를 채택하지 않는 이유**: 표준과 회사 데이터가 한 테이블에 섞이면, 자동 tenant 격리(회사 데이터만)와 baseline(전역 공유)이 같은 tenant_id 컬럼에서 충돌한다. 회사가 늘수록 부채가 커진다. 완전 분리(A)만이 "baseline 원본과 회사 결정 분리 저장"(ADR-0025)에 충실하다.

### 3. Overlay action — 4가지 결정

instance 레코드의 `action`:
- **adopt**: baseline 항목을 그대로 채택 (override 없음)
- **exclude**: baseline 항목을 이 회사가 비채택 (제외 플래그)
- **override**: baseline 항목을 참조하되 일부 필드 변형
- **add**: baseline에 없는 회사 고유 신규 항목 (`baseline_*_id` 없음, 자체 값)

### 4. Override = 필드 단위 diff (스냅샷 아님)

변형(override)은 **변경된 필드만** instance에 저장한다. 예: owner_name만 바꾸면 그 필드만 저장, 나머지는 baseline을 따른다.

**이유**: ADR-0025의 "법령 개정 시 baseline 교체로 미변경분 자동 갱신"은 필드 diff에서만 작동한다. 전체 스냅샷 방식은 변형된 항목이 baseline 개정을 못 따라가, 법 개정 시 변형 항목을 일일이 손봐야 한다. **모든 case 대응**이 목적이므로 필드 diff를 채택한다. 병합 복잡도는 공통 로직 한 곳에 가둔다.

### 5. 조회 병합 로직

회사의 RCM 조회 = **baseline − exclude + override(필드 병합) + add**.
- baseline 항목 중 이 회사가 exclude하지 않은 것을 가져오고
- override가 있으면 baseline 필드에 instance의 변경 필드를 덮어 병합
- add 항목(회사 고유)을 더한다

병합은 tenant 자동 격리(ADR-0026)와 맞물린다. 각 쿼리에 수동으로 병합을 넣지 않고, 공통 병합 로직 한 곳에서 처리한다(제로 추상화 예외 — 데이터 정합성 우선).

### 6. Unique 재설계

- baseline: `code` 전역 unique
- instance: `(tenant_id, code)` 복합 unique
- ADR-0026 미결 항목("글로벌 unique → 복합 unique") 해소.

### 7. 95통제 처리 — 하이브리드(C)

현재 controls 95건을 **baseline 초안으로 이관**한다. 사이냅소프트 RCM은 실무에서 검증된 것이므로 백지보다 나은 출발점이다. 사이냅소프트는 이 baseline을 채택한 첫 tenant instance가 된다.

**단, 이는 초안이다.** 완성된 Basic-perfect(법령·제도 완전 대응)는 충분한 조사·법령 검토가 필요한 별도 트랙이다. **구조와 콘텐츠를 분리**했으므로, baseline 콘텐츠를 나중에 다듬어도 구조·overlay는 바뀌지 않는다 — 초안이든 완성본이든 같은 구조 위에 올라간다.

## 단계적 구현 (이 ADR 위에 얹음)

한 번에 5계층을 쪼개지 않는다. 검증 가능한 단위로:

- **2-A**: Control 계층 먼저 (가장 핵심·복잡). baseline_controls / control_instances + 병합 + 필드 diff + 복합 unique를 여기서 검증.
- **2-B**: 검증되면 나머지 계층(Process·SubProcess·Risk·RiskCategory)에 동일 패턴 확대.
- **2-C**: 95통제를 baseline으로 이관 + 사이냅소프트를 첫 tenant instance로 정리.

각 단계는 데이터 보존(ADR-0023)·테스트·검증 후 다음으로 진행한다.

---

## Consequences

- RCM API 응답이 바뀐다(병합된 결과 반환). Regina 프론트는 2-A 스펙 확정 후 대응 (그 전까지 현 API 유지).
- 병합 로직·필드 diff로 조회가 복잡해지나, 모든 커스터마이징 case에 대응 가능해진다.
- baseline 콘텐츠 완성(Basic-perfect)은 별도 트랙 — 구조는 이 ADR로 고정, 콘텐츠는 후속.
- AI 자동설정 비전: AI가 생성하는 것이 곧 instance(overlay) — 기업 인터뷰 → adopt/exclude/override/add 결정.

## 미결정 (후속)

이미 해소된 항목:
- ~~병합 로직의 구체 구현 지점~~ → 공통 함수(control_resolver) 확정 (2-A-1)
- ~~override 필드 diff 저장 방식~~ → nullable 컬럼 미러링 확정 (2-A-1)
- ~~baseline 버전 관리 필드~~ → baseline_version 행 단위 컬럼 선반영 (2-B-3.5). 개정 워크플로·소급 매핑·알림 UX는 개정 트랙 미결.
- ~~RiskCategory baseline/overlay 필요 여부~~ → baseline-only 확정 (2-B-1)

남은 필수 항목 (skip 금지):
- **코드 마스터 테이블화 (필수, 2번째 tenant 온보딩 전 반드시 실행)**: risk_level·assertion 코드·통제 유형(preventive_detective/auto_manual)·주기(frequency)·ipe_relevant가 현재 String 컬럼이라 DB 레벨에선 커스터마이징을 막지 않으나, 프론트 드롭다운·검색 필터·코드→라벨 매핑에 값 목록이 하드코딩되면 고객사 커스터마이징이 막힌다. enum이 아닌 코드 마스터 테이블(tenant별 override 가능)로 전환해야 한다. String 컬럼은 유지하고 값의 출처만 테이블화하므로 스키마 파괴 없음(retrofit 아님). 그러나 프론트 필터가 여기 물려 있어 빼는 시점이 늦으면 계약 파괴가 되므로 2-B 완료 후 별도 단계로 반드시 진행한다. 2-B에서 뺐으나 skip하지 않는다.
- source envelope 전 계층 공통 규약 (id/source/baseline_id/is_overridden) — 2-B-4에서 확정
- 삭제 의미론 — baseline→exclude(hide), add→soft delete, 전 계층 공통 (2-B-3.5 문서화, CRUD 반영은 2-A-4)
