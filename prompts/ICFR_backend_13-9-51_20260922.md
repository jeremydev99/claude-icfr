# ICFR_backend_13-9-51_20260922 — 감사 컬럼(created_by·updated_by·deleted_by) 자동 기록

**필요 모델: Opus (STEP 0 + 구현 모두)** — 권한·보안급. 모든 쓰기 경로에 영향.
**push: 마스터 직접** (자동 push 금지)

## 배경
`created_by`·`updated_by`·`deleted_by`는 시스템 전체(약 52개 테이블)에서 한 번도 채워진 적이 없다. tenant_id와 같은 구조로 자동 기록한다. 이 방식은 사용자 ContextVar와 `before_flush`를 쓰며, 수동 대입은 금지한다(ADR-0025 자동 격리 패턴 준용).

## 확정된 결정
1. **값 형식**: 사용자 UUID 문자열 `str(user.id)`. 이메일·이름은 쓰지 않는다. 화면 표시는 조회 시 변환한다. users로의 FK는 걸지 않는다.
2. **사용자 없는 쓰기**: `system:<출처>` 형식의 시스템 행위자를 **명시해야만** 기록된다. 예: `system:seed`, `system:migration`, `system:bootstrap`. 출처명은 실측한 경로에 맞춰 정한다.
3. **fail-closed**: 사용자도 시스템 행위자도 지정되지 않은 채 대상 테이블에 쓰기가 일어나면 flush를 실패시킨다. `unknown` 같은 기본값으로 채우는 것은 금지한다.
4. **기록 규칙**
   - `created_by`: insert 시에만 채운다. 이미 값이 들어 있으면 유지한다.
   - `updated_by`: update 때마다 현재 행위자로 갱신한다.
   - `deleted_by`: `is_deleted`가 false→true로 바뀔 때 채우고, true→false(복구)일 때는 비운다.
5. **기존 NULL 행은 backfill하지 않는다.** 모르는 과거를 지어내지 않는다.
6. 행위자 판별은 믹스인·타입 등 구조로 한다. 테이블명 문자열 매칭은 금지한다.

## STEP 0 — 실측·설계 보고 후 멈춤 (코드·DB·설정 수정 금지)

1. **대상 테이블**: 세 컬럼이 정의된 모델·믹스인 위치와 대상 테이블 목록(개수 포함)을 확인한다. IdentityBase 계열(users, tenants, 매핑 등)에 컬럼이 있는지, 대상에 넣을지에 대한 판단 근거도 적는다.
2. **실제 타입**: 모델 정의와 최신 마이그레이션 기준 컬럼 타입, 길이, nullable을 확인한다. UUID 문자열(36자) 이상을 담을 수 있는지 본다. 모자라면 마이그레이션 필요 여부를 보고한다.
3. **운영 DB 대조**: 마스터가 실행할 조회 명령을 코드 블록으로 제시한다. 직접 실행하지 않는다. 최소한 아래 두 가지를 포함한다.
   - information_schema 기준 세 컬럼의 테이블별 타입
   - 세 컬럼 중 하나라도 값이 있는 행 수 (0 확인용)
4. **현재 tenant 자동 기록 구조**: `core/tenant_context.py`의 `before_flush` 등록 방식, ContextVar 설정 위치(`get_current_user`), 동기·비동기 전파 방식을 확인한다. 감사 기록을 같은 리스너에 넣을지 별도 리스너로 둘지, 실행 순서를 정한다.
5. **사용자 없이 쓰는 경로 전수**: 시드 스크립트, bootstrap·startup, 관리 명령·CLI, 백그라운드·스케줄 작업, ORM Session을 쓰는 마이그레이션, 테스트 fixture(conftest)를 찾는다. 경로마다 파일:라인과 부여할 `system:<출처>`를 표로 보고한다.
6. **soft delete 방식**: `is_deleted` 변경 위치가 공통 헬퍼인지, 흩어져 있는지 확인한다. bulk update(`query.update()`·`update()` 문)처럼 `before_flush`를 거치지 않는 쓰기가 대상 테이블에 있는지 전수 확인한다. 있으면 처리 방안을 제시한다.
7. **ADR 번호**: `docs/adr/`의 최대 번호를 확인한다. ADR-0035는 매뉴얼 패널 예약이므로 비어 있어도 쓰지 않고, 다음 빈 번호를 제안한다.
8. **Regina 작업 충돌**: `git fetch` 후 원격에서 새로 바뀐 파일과 이번 변경 예정 파일이 겹치는지 확인한다.

**보고 형식**: 위 1~8을 항목별로 짧게 적고, 구현 계획(파일, 커밋 분할)과 마스터가 확인할 질문을 끝에 둔다. **여기서 멈춘다.**

## 구현 (마스터 확인 답을 받은 뒤)

### 커밋 분할 (한 커밋 = 한 원인, 이 순서)
1. **행위자 컨텍스트**: 행위자 ContextVar와 시스템 행위자를 지정하는 컨텍스트 매니저를 추가한다. `get_current_user`에서 사용자 id를 설정한다. STEP 0 5번의 모든 경로에 시스템 행위자를 지정한다. 이 커밋에서는 아직 기록·강제를 하지 않는다.
2. **자동 기록 + fail-closed**: `before_flush`에 결정 4의 규칙을 적용한다. 행위자가 없으면 명확한 예외 메시지와 함께 실패시킨다. STEP 0 6번에서 bulk update가 확인됐다면 그 처리도 이 커밋에 포함한다.
3. **테스트**
   - 대상 테이블 전체를 구조로 순회해 insert, update, soft delete, 복구 시 세 컬럼 값을 검증한다(테이블명 하드코딩 금지).
   - `created_by`가 update로 바뀌지 않는지 검증한다.
   - 시스템 행위자(`system:seed` 등)가 기록되는지 검증한다.
   - 행위자 미지정 시 flush가 실패하는지 검증한다.
   - 다른 tenant 사용자로 쓸 때 tenant 격리 회귀가 없는지 검증한다.
4. **문서**: 새 ADR, ClaudeICFR.md 13.9-51 완료 처리, §14 변경로그를 작성한다. 이 프롬프트 파일도 함께 넣는다.

### 검증 (보고 시 표로)
1. 대상 테이블 전체: insert → created_by·updated_by = 사용자 id
2. update → updated_by 갱신, created_by 불변
3. soft delete → deleted_by 기록 / 복구 → deleted_by 비움
4. 시드·bootstrap 실행 → `system:<출처>` 기록, 실패 없음
5. 행위자 미지정 쓰기 → flush 실패, 예외 메시지 확인
6. 기존 NULL 행 불변(backfill 없음)
7. tenant 격리 테스트 회귀 없음
8. 백엔드 전체 순차 2회 통과
9. 로컬 컨테이너가 기동되면 실제 API로 한 건 생성·수정·삭제 후 DB 값을 확인한다. 기동이 안 되면(13.9-24) "미확인"으로 적고, 운영 확인용 조회 명령을 코드 블록으로 준다.

### push 전 (마스터 실행 — 명령만 제시)
- 스키마 마이그레이션이 없으면 백업 없이 push해도 된다. 마이그레이션이 생겼다면 백업 → push 순서로 명령을 준다.
- push 직전에 `git fetch` 후 `git log --oneline HEAD..origin/main`로 원격 변경이 없는지 확인하는 명령을 준다.
- 배포 후 확인: 운영에서 한 건 수정 후 해당 행의 세 컬럼을 조회하는 psql 명령을 코드 블록으로 준다.

**자동 push 금지.** 로컬 커밋까지만 하고, 커밋 해시와 검증 표로 보고한다.
