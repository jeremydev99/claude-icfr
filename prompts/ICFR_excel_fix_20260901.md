## 0. 확정된 원인

조사로 특정 완료. **파서는 정상이고 호출부의 인자 계산이 원인이다.**

```python
# seeds/seed_baseline.py:136-138  → 93건
data_start = _find_data_start(ws, header_row, mapping["process_code"])   # → 8
parsed = _parse_rcm_sheet(ws, data_start - 1, mapping)                   # → 7 전달

# app/api/rcm.py:1097-1100  → 0건
sheet_name, header_row, mapping = found                                  # header_row = 6
parsed = _parse_rcm_sheet(ws, header_row, mapping)                       # → 6 전달
```

`_parse_rcm_sheet`(rcm.py:925-927)는 두 경로 공용이며 `min_row=header_row+1`부터 순회하다
`row[p_col] is None`이면 `break`한다. 대상 파일은 7행이 2차 헤더(50열 이후에만 값 존재)라
6을 넘기면 첫 반복에서 즉시 break된다.

동일 파일·동일 파서로 인자만 바꾼 실측:
- `_parse_rcm_sheet(ws, 7, …)` → controls 93 / processes 8 / risks 85 / errors 0
- `_parse_rcm_sheet(ws, 6, …)` → 전부 0

## 1. 범위

**포함**
- `upload-excel` 호출부에 데이터 시작 행 보정 적용
- **파싱 0건을 성공으로 반환하지 않도록 수정** (§3)
- 실제 파일 구조를 쓰는 멀티헤더 회귀 테스트 신설

**제외**
- 13.9-10-b (`upload-excel` write→read 소스 분리, xfail `test_excel_upload_commit`)
  → 별건. 이번 수정으로 해소되지 않는다
- `upload-excel`의 overlay 전환 → 별건

## 2. 수정 1 — 데이터 시작 행 보정

`_find_data_start` 로직을 `upload-excel` 호출부에도 적용한다.

**로직을 복제하지 말 것.** 현재 `seeds/seed_baseline.py`에만 있는 `_find_data_start`를
양쪽이 공용으로 쓰도록 한 곳에 두고 참조한다. 복제하면 한쪽만 고쳐지는 상황이 생기고,
이번 결함이 정확히 "두 호출부가 다르게 계산해서" 발생한 건이다.

배치 위치는 실측으로 판단할 것 — `_parse_rcm_sheet`가 이미 어디에 있는지 확인하고
같은 모듈에 두는 것이 자연스러운지, 별도 위치가 나은지 근거와 함께 보고.
ADR-0020 준수: 클래스·패턴 금지, 함수 이동/공용화만.

**seed 경로의 동작이 바뀌면 안 된다.** 현재 93건이 정상 동작하므로 회귀 가드가 필요하다.
기존 seed 테스트가 이를 보장하는지 확인하고, 없으면 추가할 것.

## 3. 수정 2 — 0건을 성공으로 반환하지 않는다

현재 동작 (조사 실측):

```
POST /api/rcm/upload-excel (mode=preview)
HTTP 200
{"summary": {"total_rows": 0, "valid_rows": 0, "errors": [], "warnings": []}, "preview": []}
```

**에러도 경고도 없이 200이다.** 사용자에게는 "업로드 성공, 0건"으로 보인다.
93건짜리 RCM을 올렸는데 성공했다고 표시되고 아무것도 들어가지 않는다.

**파싱 결과가 0건이면 실패로 다룬다.** 수정 1로 이 파일은 해결되지만,
다른 파일이 다른 이유로 0건이 되어도 같은 문제가 반복된다. 원인과 별개로 막아야 한다.

구현 시 판단할 것:
- HTTP 상태 코드를 바꿀지(400/422), 200 유지하고 errors에 담을지
  → **기존 에러 반환 규약을 따를 것.** 이 엔드포인트가 다른 실패를 어떻게 반환하는지
    확인하고 동일한 형태로 맞춘다. 이 건만 다른 규약을 쓰면 FE가 분기해야 한다
- 메시지는 원인을 짐작할 수 있게 쓸 것. "0건" 만으로는 사용자가 다음 행동을 알 수 없다
  (예: 시트·헤더는 인식됐으나 데이터 행을 찾지 못했다는 취지)

**FE 영향** — Regina가 `EXCEL_UPLOAD_LOCKED`로 업로드 버튼을 잠가둔 상태라 즉시 영향은 없다.
다만 응답 형태가 바뀌므로 완료 후 공유 대상이다.

## 4. 수정 3 — 멀티헤더 회귀 테스트

**현재 Excel 테스트 8건이 전부 단일 헤더 픽스처(`_make_test_excel`)를 쓴다.
멀티헤더를 커버하는 테스트가 0건이며, 이것이 결함이 살아남은 이유다.**

신설할 테스트:
1. 2차 헤더 행이 있는 구조에서 데이터가 정상 파싱될 것
2. 파싱 0건일 때 성공으로 반환되지 않을 것 (§3 검증)
3. 단일 헤더 구조도 계속 정상 동작할 것 (기존 동작 회귀 가드)

**픽스처는 실제 파일 구조를 재현할 것.** `2026_설계평가_RCM_리스트.xlsx`와 같은 형태 —
1~2행 메타, 3~4행 공백, 5행 설명 밴드, 6행 주헤더, 7행 2차 헤더(일부 열만 값), 8행부터 데이터.

실제 파일을 테스트에서 직접 읽을지 합성 픽스처로 재현할지는 판단하되, **근거를 보고할 것.**
실파일 의존은 파일이 바뀌면 테스트가 깨지고, 합성 픽스처는 실제 구조와 어긋날 수 있다.

## 6. 검증 조건

1. 대상 파일을 `POST /api/rcm/upload-excel` (mode=preview) 로 처리 → **93건 반환**
   — 조사와 동일하게 TestClient 엔드포인트 경유로 확인할 것. 파서 직접 호출은 검증이 아니다
2. 파싱 0건인 입력 → 성공 응답이 아님
3. 단일 헤더 파일 → 기존대로 정상 파싱 (회귀 없음)
4. `seed_baseline.py` 경로 → 여전히 93건 (공용화로 인한 회귀 없음)
5. 전체 pytest 통과, xfail은 1건 유지 (`test_excel_upload_commit` — 10-b 별건)

**1번은 조사에서 0건이 재현된 바로 그 경로다.** 여기서 93건이 나와야 수정이 실증된다.
